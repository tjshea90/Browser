alpha67: the whole app is compiled while it installs, the longer install for a faster browser that you asked for. Until now Android compiled only about 2500 of the app's 15000 methods when an update installed (the ones my start-up profile marked hot) and ran all the rest in its slow interpreter until the tablet was idle and charging. Now one more rule marks every method hot, so Android compiles ALL of it while the update installs. In the test phone that took 1 second longer (1.2 to 2.3 seconds), made 12 MB of compiled code instead of 3 MB, and changed nothing else I could measure: start-up, opening a link in the running browser and memory were the same, so I expect about 10 to 20 seconds more install time on the tablet and a little less lag the first time you use a menu, the tab list or a settings screen (not measured on the tablet). The start-up file the updater sends got smaller (4 KB). I also tested the other half of your idea, whether the first start after an update is slower than later ones (so a warm-up run right after the update could help): it is not, so I did not build one. This release also carries the Swoop keyboard engine fix made after alpha66 (Kestrel's own keyboard behaves as before) and a new Diagnostics line, start oat, with the sizes of the compiled-code files: send it after the update to prove that the whole app was compiled (about 12 MB for base.odex; about 3 MB means the old small profile). IMPORTANT: like alpha65, this only works for updates that come FROM alpha65 or alpha66, because they carry the updater that sends the start-up file: so the update from alpha66 to alpha67 is the first one compiled whole. NOT proven on the tablet: Android Go may ignore the file (then the nightly compile when the tablet is idle and charging does the same job later, now for the whole app). If an update ever fails to install, tell me the exact words Android shows.
