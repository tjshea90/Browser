I ran the tablet-shaped test phone on GitHub six ways (a whole day of use before and after, the video suite, a packaging comparison, a start-up comparison, an engine settings sweep, a start-up profile) and changed only what a measurement or a stack sample supported. What is new: (1) the engine's 14 MB code bundle is stored uncompressed in the app file, so the engine maps it instead of unpacking it into every engine process: in the test phone a warm start was 11 percent faster and about 28 MB less memory was used after browsing. (2) A start-up profile of the 6700 methods the app, the engine's Java and the player really use is built in; Android turns it into machine code when the tablet is idle and charging (Diagnostics line start art says when it has), so the first days after an update should feel quicker. (3) The ad blocker's extension answers the engine through one message listener instead of 24 (less work per page), no longer runs its player scripts inside human-check frames such as Cloudflare (that was a bug), and scans class names less often. (4) The engine no longer lists its whole page cache (up to 40000 files) at every start. (5) Engine settings version 10: no login or form-history machinery (nothing is stored anyway) and no captcha telemetry actor. (6) Small start-up changes: the settings files are read earlier, the Recents icon is set later, and the engine's config file is read on a spare thread before the engine starts. NOT proven on the tablet: the test phone is a fast x86 machine with a software GPU, so start-up and page speed looked the same there; the gains above are measured memory and engine-create time, the rest is expected on the tablet's slower cores.
