## ANS58c: logged out after another app (a real bug of ours, fixed)
- What the code did: BrowserActivity.onTrimMemory(level >= MODERATE) while the app is not in front put the tab in front to SLEEP (`hibernate`: close its engine session; for a private tab the history was dropped and the address kept to be loaded again), and `enforceLiveLimit` did the same to the least recently used other tabs. A normal tab keeps its cookies on disk, so it comes back logged in. The engine forgets EVERYTHING private (cookies, logins) when its LAST private session closes, so a private tab that was put to sleep came back logged out.
- The fix: (1) a private tab is never put to sleep by the memory handling (core LiveBudget.mayHibernate / mayHibernateInBackground; hibernate itself refuses a private tab); (2) ONE hidden private session, the "anchor" (BrowserActivity.syncPrivateAnchor), stays open while any private tab exists, so a session that has to be replaced (the page's process was killed by Android while the app was away: sessionGone) can never be the last private session; it closes with the last private tab (the engine then forgets what was private, as before).
- What it cannot do: if Android kills the WHOLE app process while it is away, everything private is gone (nothing is written to disk for a private tab, on purpose).
- Proof: core LiveBudgetTest, OwnerRulesTest guard; emulator lab suite pv (soaklab /pv login-cookie page, `am send-trim-memory MODERATE / COMPLETE` after Home, then back: a private tab is not slept and not reloaded and still has its cookie; a normal tab is the control).

## ANS58a / ANS58b: slow check and laggy typing (no data from the tablet yet: hypotheses and the first cheap measure)
- Cloudflare's visitor check (Turnstile: `challenges.cloudflare.com`, an iframe with nested about:blank frames, or the full-page "Just a moment" interstitial) runs a heavy script in the engine's ONE content process on a 4 x Cortex-A53 tablet, behind the 5 Mbit hotspot and the phone's page proxy; typing into a page field goes through that same content process, so a busy check makes the letters late. That part is the engine's and the site's.
- What is OURS and measurable: the Kestrel Shields extension injects 12 scripts (about 450 KB of script text: vfind, content, guard-main, gate-main, codec-main, scriptlets-main 56 KB, players, seekbar, videobar, turn, player) into EVERY page AND EVERY FRAME at document_start / document_idle (all_frames true; the MAIN-world ones also into about:blank frames). A check page has several frames, so the tablet parses and runs the whole set again for each. The MAIN-world ones also PATCH prototypes (HTMLMediaElement.play, canPlayType, window.open ...), which a bot check may notice and answer with more work.
- First cheap measure (this alpha): `exclude_matches` for the human-check hosts in all 8 content-script blocks of kestrel-shields/manifest.json: challenges.cloudflare.com, hcaptcha, recaptcha, arkoselabs / funcaptcha, DataDome (captcha-delivery), PerimeterX / HUMAN: none of our scripts runs in those frames (no video there, nothing to hide). `match_origin_as_fallback` makes the about:blank children of such a frame follow their parent's origin.
- NOT settled, needs data: the interstitial page of the SITE itself (same origin as the site) still gets all scripts. If the owner's next Diagnostics (right after a slow check) shows the content process ("tab") near 100 % of a core, it is the check itself; if the parent process or the UI thread is busy (ui.stall / ui.late, frames.jank), it is ours and the next step is the lazy injection below.
- Next step if it is ours (ANS58e, idea): load the video scripts (gate, codec, vfind, videobar, turn, player, players, seekbar: about 150 KB) only into documents that really have a video / audio element or a MediaSource, with the MAIN-world gate in place before the first play() (a tiny always-on probe + a registered content script added at the first media element), and the cosmetic scriptlets library only for hosts that have scriptlet rules.
