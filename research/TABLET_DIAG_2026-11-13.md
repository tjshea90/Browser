## 1. Storage: the update cannot install (the blocker for every fix since alpha27)
- `Storage: 1.62 GB free of 27.75 GB; free + caches Android can clear: 1.62 GB` (so there are no clearable caches; Kestrel's own 228.1 MB cache is NOT counted by Android as room it may take).
- This app: package 94.4 MB + unpacked libraries 131.7 MB + data 62.3 MB + cache 228.1 MB (= 0.52 GB that an uninstall would give back, plus compiled code).
- Android's rule (measured on the emulator image, research/UPDATE_STORAGE.md, `UpdateLogic.storagePlan`): keep 10 % of the data partition free after the install (here 2.77 GB) + the installer's staged copy of the APK (99 MB for alpha28) + the libraries it unpacks (131.7 MB) + about 48 MB of compiled code = **about 3.0 GB, 3.1 GB while Kestrel keeps its own downloaded copy**.
- So: an update in place is short by **about 1.5 GB**. Uninstall first (Updates sheet "install the other way") gives back about 0.5 GB and a fresh install needs the same ~3.0 GB, so it is still about **0.9 GB short**: the other way would leave the owner with NO Kestrel G installed and the installer still refusing. (Their earlier "I installed it fine from GitHub after uninstalling" happened when the tablet had more free room.)
- Not yet confirmed on this tablet: the 10 % rule itself (the emulator measured it; the owner's long-standing "newer versions never install over the old ones" fits it). The Updates sheet prints Android's own refusal and the number the first time Install is tried.
- Only real fixes: the owner frees about 1.5 GB (downloaded movies in Downloads, unused apps, photos; a microSD card if the tablet has a slot), or Kestrel gets smaller. Kestrel can help with: a one-tap "Clear Kestrel's cache" (228 MB now, the engine's disk cache may grow to 500 MB), a listing of its own biggest downloads, and honest after-uninstall numbers (AH1b).

## 3. Video and GPU (replaces the guesses in VIDEO_AUDIT.md sections 1 and 3)
- Hardware decoders on this tablet: H.264 `MTK.VIDEO.DECODER.AVC` 2048x1088@145, H.265 `MTK.VIDEO.DECODER.HEVC` 2048x1088@145, **VP9 `MTK.VIDEO.DECODER.VP9` 2048x1088@68 (confirmed hardware)**, VP8 `MTK.VIDEO.DECODER.VPX`, MPEG-4, MPEG-2, MP3. AV1: software only (so never offered). AAC/Opus/Vorbis/FLAC: software (cheap). AC-3 / E-AC-3: none (a site stream with only Dolby audio would be silent or fail).
- Widevine: L3, Google 15.0.0, HDCP unprotected (so protected video is standard-definition only; nothing we can change).
- GPU: ARM Mali-G52 MC2, OpenGL ES 3.2 (pages see "Mali-G51, or similar": Firefox hides the exact chip).
- BUG seen: `Video: codecs offered to sites: device decoders unknown: engine defaults, no AV1 [hardware decoders unknown]` although the probe read 26 decoders (`video decoders AHVi 26 decoder(s)` in the events, five times). ROOT CAUSE (reproduced on the emulator from a cleared app, event `engine video-prefs-failed java.lang.IllegalThreadStateException: Must have a Handler`): `GeckoPreferenceController.setGeckoPref` sends its message and THEN calls `.map` on a GeckoResult, which throws on a thread without a Looper; the decoder probe re-applied the video rule from the IO pool, so only the FIRST pref (`media.mediasource.vp9.enabled`) arrived and the text, written last, never changed. FIXED (AH1d): `GeckoEngine.hopToMain` guards `applyVideo/applyNetwork/applyLab/applyScrollFeel`, the text is written first, one try per pref. Emulator after the fix: `codecs offered to sites: VP9 as the engine decides, no AV1 (software only here), no H.265 (software only here) [hardware decoders ahvi]` and no failure event. On the tablet the engine was running with VP9 on (hardware) and the engine defaults for H.265/AV1, which is what the rule would have chosen anyway: no behaviour was lost, only the Diagnostics line was wrong.

## 6. Owner message 22 (2026-11-13T07:18Z): "Doraby doesn't load movies at all, one site said incompatible browser or the browser can't access cloudflare"
Evidence gathered without the tablet (headless Chromium through the sandbox proxy for the page structure, the Disconnect list from shavar-prod-lists for what Firefox's own protection names, the bundled filter snapshot for what OUR lists do):
- **How Doraby plays a movie.** The watch page (`https://doraby.com/<slug>/`) shows six "servers" (Vidfast, 111movies, Vidsrc, Videasy, Vidzee, Vidcore). `servers.min.js` just does `jQuery("#iframe").attr("src", Servers.<name>)` after the owner taps the big play button; the `Servers` object holds the embed addresses: `vidfast.vc/movie/<tmdb>`, `www.vidy.st/movie/<tmdb>`, `vidcore.net/movie/<tmdb>`, `embed.vidrift.net/embed/movie/<tmdb>?autoPlay=true`, `play.xpass.top/e/movie/<tmdb>`, `furniturebeast.nl/embed/movie/<imdb>`. So the movie is a CROSS-SITE frame; the page itself only needs jsDelivr (lazyload, bootstrap, swiper) and the frame needs its own player libraries (typically hls.js from jsDelivr or cdnjs) and, behind Cloudflare, the visitor check.
- **Cloudflare's visitor check lives on `challenges.cloudflare.com`** (script `/turnstile/v0/api.js`, frame `/cdn-cgi/challenge-platform/...`). When that host is blocked, Cloudflare's own page says to unblock it ("Please unblock challenges.cloudflare.com to proceed") - the owner's "the browser can't access cloudflare" - and players that give up show "incompatible browser" style messages.
- **Firefox's own Disconnect "Content" list names `cloudflare.com`** (entity "Cloudflare": covers challenges.cloudflare.com and cdnjs.cloudflare.com) next to `cdn.jsdelivr.net` ("Volentio JSD"), `jwpcdn.com` (JW Player) and `gstatic.com`. alpha27 and earlier asked Firefox for STRICT INCLUDING that category (research/DORABY.md), so Firefox's tracking protection refused those hosts for every page and frame: the same cause as doraby.com's missing photos and icons, one step deeper (the player frame). alpha28 dropped the category (`antiTracking = STRICT without CONTENT`, core/shield/EtpCategories) and alpha29 adds the per-site Shields-off switch (also Firefox's own protection). The owner's tablet could not install either (1.62 GB free): the report is probably from alpha27. NOT observed on a device; the Page report (alpha28+) will name any file still refused.
- **Our own lists do not block any of it** (new regression test `DefaultListsRegressionTest.theMoviePlayersOfDorabyAndCloudflaresVisitorCheckAreNotBlocked`: the six embed addresses as frames, Turnstile's script, frame and challenge-platform calls, the jsDelivr and cdnjs copies of hls.js and video.js: none blocked).
- **Not the "Embeds wait for a tap" guard**: `EMBED_RULES` in background.js lists only YouTube, Vimeo, Dailymotion, Facebook, Instagram, TikTok, Spotify, SoundCloud, Disqus and Google Maps embeds; Doraby's players are not in it.
- Still possible after the above (needs the tablet's Page report on the watch page after tapping play, and the exact message of the other site): the player's own anti-adblock or anti-devtools checks, the popup/redirect guard refusing a hop inside the frame, autoplay with sound inside a frame without `allow=autoplay` (needs a tap in the frame), hls.js needing a codec the tablet lacks (Widevine L3 only, no AC-3/E-AC-3, AV1 software only).
