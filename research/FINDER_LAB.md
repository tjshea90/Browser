# Finding the real video on a page (RX3-V1 .. V7, research/REVIEW-EXTERNAL-3.md part V) - design notes and measurements
Newest section last. ASCII only. The finder lab pages themselves are `tools/sitelab/vidlab_srv.py` (EY-21); new pages for V1-V5 are listed in section 0 when they exist.

## 0. Where things are (read 2026-11-14)
- Page side: `content.js` `report(v)` on every `loadedmetadata` sends `{k:'vid', u, w, h, d, l, p}` -> `background.js` relays -> `ShieldsBridge.onVid` -> `mediaInfo` -> `VideoFlow` -> `MediaList.applyInfo`.
- App side: `MediaList` (48 ranked entries, `usable()` = what the dock badge counts), `MediaRank.rank` (sheet: `main` and "Other files"), `MediaCandidate.touched` (somebody showed interest: never evicted, never hidden).
- The defect V1 fixes: `applyInfo` set `touched = true` for EVERY element that reported, so a hover preview, a muted looping hero video, a GIF-style loop or a 15-30 s pre-roll at 720p was "played, long or sharp" in `usableUnsorted` and stayed in the badge.

## 1. RX3-V1 - what a `<video>` is for (alpha42)
Facts the page sends with the report (all numbers, no address beyond the page the report already named): bit flags `f` = muted 1, loop 2, autoplay 4, controls 8 (the native attribute OR a known player root around it: jwplayer, video-js, plyr, mejs__container, flowplayer, shaka-video-container, html5-video-player), visible 16 (not display:none / visibility:hidden, laid out), ad 32; rendered size `rw` x `rh` in CSS pixels; `vp` = percent of its box inside the viewport.
The ad flag: an ancestor (8 levels, never body) whose class or id, split at every non-alphanumeric character, holds the token `ad`, `ads`, `advert`, `advertisement`, `adslot` or one of the ad-state classes of the players (`jw-flag-ads`, `vjs-ad-playing`, `ima-ad-container`, `plyr__ads`, `ad-showing`, `ad-interrupting`). Whole tokens only: `address`, `headline`, `download`, `add-to-cart` do not match.
`core/media/VideoRole.kt` (pure): `decide(facts, durationMs)` -> PLAYER | DECOR | AD. No facts (an old extension, a report from somewhere else) = PLAYER (nothing changes). AD = ad flag. DECOR = (loop && muted && !controls) || (muted && autoplay && !controls && 0 < duration <= 30 s) || (rendered area > 0 and under 160 x 90).
`MediaList.applyInfo(..., role)`: PLAYER sets `touched` as before; DECOR / AD record the role and do NOT set `touched`; the latest report wins; `touch(url)` (the owner long-pressed, opened or downloaded it) still sets `touched`, and `touched` always shows. `usableUnsorted` hides a DECOR / AD entry before the "played, long or sharp" exemption (a stream too). `MediaRank.junk` sends them to "Other files" (never deleted: one tap). `value()` makes them the first to be evicted from a full list.
Cost of a wrong guess: a muted autoplay clip of under 30 s with custom controls that nobody recognised is hidden from the badge and sits one tap away under "Other files on this page".

### 1.1 Emulator proof (2026-11-14; Android 10 x86_64 emulator, GeckoView 160 debug build: NOT the tablet)
Lab: `tools/sitelab/guardlab.py` page `/finderlab` (four REAL media elements, 20 s silent audio each, described differently by the page itself) + `tools/emu/playerlab_emu.py --path /finderlab --grep "video info"`; the app logs one line per report: `video info role=... length=...s counted=N of M` (no address).
| Element | What the page says | Role the app decided |
| :- | :- | :- |
| `<video muted loop autoplay>` 300x100, no controls | a hero loop | DECOR |
| `<video controls>` 300x140 | a player | PLAYER |
| `<video controls>` inside `div.sidebar.ad-slot` | an ad slot | AD |
| `<video controls>` 120x60 | thumbnail-sized | DECOR (area 7200 < 14400) |
Final line of the run: `counted=1 of 4` - only the player counts for the dock badge; the other three stay in the list for "Other files" (the sheet), nothing deleted.
Defect found by the first emulator run and fixed (with a JVM test): the element's report can arrive BEFORE the extension reported the file (loadedmetadata vs the response), and `applyInfo` then dropped it (`counted=0 of 0`, two roles lost). `MediaList` now keeps what an element said about a file it does not hold yet (32 files, forgotten with the list) and applies it when the file is added.
Tests: core `VideoRoleTest` (7), `MediaListTest` (+9), `MediaRankTest` (+4); web-tests `videofacts.test.js` (9, real Chromium), `background.test.js` (+1 relay). NOT done: a real site's hover previews and pre-rolls (the sandbox cannot reach one that plays them), the tablet.

## 2. RX3-V2 - verify before counting (alpha42)
Problem (read in the code): an address found only in the page's text (a link to `.mp4`, an og tag, a string in a script: the extension's `dom` reports, `source "dom"`) has no length and no media type; `MediaList.usableUnsorted` treated an UNKNOWN length (-1) as usable, so a page with one link to an animated teaser showed the download badge.
Rules (`MediaCandidate.fromMarkup`, `.verified`): an entry is VERIFIED when it was really requested (seen on the wire; `fromMarkup` false) OR a player reported it / the owner touched it OR (a plain file) its length is known and at least 100 KB. `MediaList.usableCount()` (the dock badge) counts verified, non-decoy entries only. Unverified entries stay in `usable()` (the sheet) and `MediaRank` sends them to "Other files" (the sheet is never empty: the fallback keeps the best one on top). A file under 100 KB whose length is learned is dropped from the sheet as before.
The cheap check (`VideoFlow.verifySoon/verifyNow`): when a markup entry is added, 2.5 s later (and never while the page is still loading, up to 6 retries 2 s apart) a page with NOTHING verified gets up to three one-byte Range requests (`MediaList.unverifiedToCheck(3)`, newest first) with the player's own headers; the answer's `Content-Range` total goes to `MediaList.setLength` (which bumps the list version so the badge recounts). Same request the sheet already made for the entries on top of it (`sized` set shared: nobody is asked twice). Private tabs ask through the private fetcher. Cost: three one-byte requests per such page.
Wrong-guess cost: a real video that is only linked, whose server ignores Range and sends no Content-Length, stays out of the badge until it is played or long-pressed; it is still in the sheet.
Tests: core `MediaListTest` (+5), `MediaRankTest` (+2). Emulator: lab page `/teaser-link` (section 2.1 when run).

### 2.1 Emulator proof (2026-11-14; Android 10 x86_64 emulator, GeckoView 160 debug build: NOT the tablet)
Lab: `/teaser-link` (two links, no player: `/teaser.mp4` 30 KB and `/bigfile.mp4` 700 KB, both answer `Range: bytes=0-0` with `Content-Range`), driver `tools/emu/playerlab_emu.py --path /teaser-link --grep "media verif|video info"`.

## 3. RX3-V5 - advertising found in the playlist, and an early look at stream playlists (alpha43)
Problem (read in the code): `Hls.parseMedia` ignored every advertising tag; an ad run was dropped only AFTER its first segment was downloaded and the MP4 writer saw another codec setup (`StreamEngine.skipRestOfRun`), and server-side ads from the same encoder passed untouched; live, protected and clip-sized streams always counted for the badge.
### 3.1 Markers (`core/media/AdMarkers.kt`, `Hls.parseMedia`, `Hls.Seg.ad`)
`#EXT-X-CUE-OUT:30` / `DURATION=30` starts a break, `#EXT-X-CUE-IN` ends it, `#EXT-X-CUE-OUT-CONT:ElapsedTime=6,Duration=30` (or `6/30`) continues one, `#EXT-OATCLS-SCTE35:<base64>` is decoded for a splice_insert (out_of_network_indicator, break_duration in 90 kHz ticks; verified against a REAL vector from the SCTE-35 documentation: out, 60.29 s), `#EXT-X-DATERANGE` with `SCTE35-OUT` starts and `SCTE35-IN` ends one (`DURATION` / `PLANNED-DURATION` bound it). A break with a known length ends when it is used up (a segment may overshoot by up to a second); with no length it ends after 3 minutes (a mistake in the playlist, not an hour of advertising). An interstitial DATERANGE (`X-ASSET-URI`, class `com.apple.hls.interstitial`) marks nothing: that advertising is a separate asset, not these segments. `#EXT-X-ASSET`, `#EXT-X-SPLICEPOINT` and SCTE-35 time_signal payloads are NOT read.
### 3.2 `core/media/AdRuns.kt`
`find(media)` -> segment ranges to leave out: (1) the marked segments (given up when they cover more than half the time), (2) a RUN (segments between discontinuities) from another SOURCE than the one holding 60 % of the playing time (source = registrable domain via `Psl` + the directory with digits folded), at most 2 minutes and at most a third of the dominant source's time, never the longest run. Never the whole playlist, never more than half of it. `withBreaks` makes the first segment after each range a new run (the time stamps of what comes back do not continue); `note` writes "Left out 1:30 of advertising (2 breaks)".
`StreamEngine.prepare` runs it on the parsed playlist, pre-seeds `job.skipped` (so those segments are never requested: at 3 Mbit/s a 30 s ad is about 11 MB of a 5 Mbit/s link) and joins the note to the row when the download finishes. A resumed download recomputes the same ranges from the stored playlist text.
### 3.3 Early look (`VideoFlow.lookSoon/lookNow`, `MediaList.applyStream`)
3 s after an HLS playlist is added (never while the page loads, at most 6 per page, 3 per round) the app reads it: a media playlist as it is, a master's lowest quality (the same two small requests the sheet makes). It records live / protected / length / advertising on the candidate; `MediaCandidate.unfit` (looked at AND (live OR protected OR under 20 s)) is not counted for the badge and goes under "Other files". Before the look nothing is known and everything counts as before.
### 3.4 Proof
JVM: `AdMarkersTest` (5, incl. the real SCTE-35 vector), `HlsTest` (+8), `AdRunsTest` (14), `StreamEngineTest` (+3: marked break never requested and the row says so; a foreign-site run never requested; no markers = whole file, no note), `MediaListTest` (+3), `MediaRankTest` (+1). Emulator lab `/hls-lab` (three playlists, segments never requested; Android 10 x86_64 emulator, GeckoView 160, NOT the tablet): `media look live=false length=120s advertising=12s in 1 breaks counted=3 of 3`, then `length=12s ... counted=2 of 3`, then `live=true ... counted=1 of 3` - only the 2-minute film stays counted.
NOT done: a real encrypted stream with real MPEG-TS ads through the MP4 writer on the device (the engine tests use plain bytes); the sheet does not yet show the advertising time next to a quality row.

## 4. RX3-V3 - which element actually plays (alpha44)
`content.js`: every element gets a small whole number (`el`, a WeakMap counter: nothing else about it leaves the page) and every metadata report carries it; a trusted `playing` event starts a 3 s check, and when the element is still playing THAT file and its clock moved 2.5 s, the same report goes again with `ev:'played'` (once per element and file; a seek, a loop or a pause under 3 s sends nothing). `background.js` passes `ev` ('played' only) and `el` (clamped) on.
App: `MediaCandidate.played / element / areaPx / playedSeq`; `MediaList.applyInfo(..., played, element, areaPx)` (the area is the part of the picture that was on screen: width x height x view percent). `MediaList.primary()` = the played, non-decoy file with the largest area, then the longest; `MediaRank.rank(..., primary)` moves it to the top of the sheet. The duration jump: the SAME element played a file under 90 s and LATER plays one at least three times as long -> the earlier file is an advertisement (role AD: not counted, "Other files"); never when the owner showed interest in it, never between two different elements, never for an earlier file of 90 s or more (two parts of one film).
Tests: web `played.test.js` (5, real Chromium), `background.test.js` (+1), core `MediaListTest` (+6), `MediaRankTest` (+2). Emulator lab `/preroll-main` (section 4.1 when run).

### 4.1 Emulator proof (2026-11-15; Android 10 x86_64 emulator, GeckoView 160 debug build: NOT the tablet)
Lab `/preroll-main` (tools/sitelab/guardlab.py): ONE `<video>` plays a 15 s clip, and after 8 s of REAL playback (tied to `timeupdate`: the emulator stalls for seconds at a time) the page gives the same element a 60 s file. App Health:
`video info el=1 role=PLAYER length=15s counted=1 of 1` -> `video info PLAYED el=1 role=PLAYER length=15s counted=1 of 1` -> `video info el=1 role=PLAYER length=60s counted=2 of 2` -> `video info PLAYED el=1 role=PLAYER length=60s counted=1 of 2`: the same element number on all four lines, and after the film's played report only ONE of the two files counts (the 15 s clip became an advertisement).
Defect found by the first runs and fixed (with a JS test): the 3 s check looked at the clock ONCE; on a slow tablet 3 s of waiting can be less than 2.5 s of film and the report was lost for good. It now looks again every 1.5 s, up to 8 more times, while the element still plays the same file.
Lab lesson: a switch timed by a clock (6.5 s) came before the first file even loaded on the cold-started emulator; tying it to `timeupdate` made the run meaningful.
NOT done: a real site's pre-roll (the sandbox gets none), the tablet.

## 5. RX3-V4 + RX3-V6 - blob: players matched to playlists, clips next to a film, soft words (alpha45)
Problem (read in `content.js` and `MediaRank`): a player that feeds a `blob:` address (a MediaSource: hls.js, shaka, dash.js, most embeds) reported NOTHING, because `content.js` dropped every `src` that did not start with "http" (twice: the metadata report and the 3 s "played" report), so the app could never say which of the playlists
the page loaded is the one playing; and every HLS/DASH playlist went to the top of the sheet, an advertising playlist and a trailer next to the film.
V4 change: (1) `content.js` reports a blob: element as `u:'blob'` (only the word, never the address) with the element's length, picture height, facts and element number, and says "played" after 3 s of real playback (the played key of a blob also holds its
length, so an advertisement and then the film on one blob address are two reports). (2) `MediaList.applyBlob(height, durationMs, role, played, element, areaPx)` matches the player to the stream playlists the early look has read: the length within 1.5 s or 3 percent of the
player's, then (a tie-breaker only, never a reason to lose the match) the playlists whose variants list that picture height; the matched playlists get the element's role / played / number, so `primary()` and the pre-roll rule of V3 work for them. What a player said is
remembered (8 players, newest kept): a playlist the early look reads LATER is matched when its look arrives (on the slow tablet the player reports well before the look). (3) The early look now also reads DASH manifests (`Dash.parse`: length, representations' heights, live/protected) and keeps the
heights of an HLS master's variants (`MediaCandidate.heights`). (4) `MediaList.clipNextToFilm`: a stream playlist, read, under 60 s, while another readable stream of 5 minutes or more (saveable, not decoration) is on the page is not counted and goes under "Other files"; never what really played, never what the owner pressed.
V6 change (`MediaRank.SOFT_WORDS`): vast, vpaid, imasdk, adunit, ad_type, adid, creative, bumper, intro, idle, loop, bg, hero, background, snippet, trailer as WHOLE words of the path or query count only when the file is ALSO under a quarter of the biggest
file and nobody vouches for it (not touched by a player, not played, not pressed by the owner); never alone, never the biggest, never a file of unknown size. Found by the first run: an existing test (a pressed `loop.mp4`) failed, hence the vouching rule.
Proof: core `MediaListBlobTest` (14: matching, tolerance 1.5 s / 3 percent, height tie-breaker, no match lost to an unlisted height, no heights known, report before the look, DASH, ad then film on one element, decoy role, live element, bounded memory, clip rule, what is spared, a protected long stream is no film),
`MediaRankTest` (+4), web `blob.test.js` (4, real Chromium: the word blob and never the address, played once, ad then film on one element, paused < 3 s not played and http sources unchanged).
### 5.1 Emulator proof (2026-11-15; Android 10 x86_64 emulator, GeckoView 160 debug build: NOT the tablet)
Lab `/blob-lab` (tools/sitelab/guardlab.py): a `<video>` on a blob: address made from a 300 s silent file, next to two playlists the page fetched (45 s and 300 s). App Health, in the order the slow emulator produced them (the PLAYER reported BEFORE the look, the rematch path):
`video info-blob el=1 role=PLAYER length=300s h=0 matched=0 counted=2 of 3` -> `video info-blob PLAYED el=1 ... matched=0 counted=2 of 3` -> `media look HLS ... length=300s heights=0 ... counted=2 of 3 playing=300s` (the film's look matches the waiting player: `primary()` is the 300 s stream)
-> `media look HLS ... length=45s ... counted=1 of 3 playing=300s` (the 45 s clip next to the film is no longer counted). (heights=0: the lab's playlists are media playlists without a master.)
NOT done: a real site's hls.js / shaka page (the sandbox cannot reach one that plays), the tablet; DASH is unit-proven only (no DASH lab page); the order "playlist read first, then the player" is unit-proven only on the emulator run.

## 6. RX3-V7 - a finder corpus with two numbers (alpha45)
`core/src/test/.../FinderCorpusTest.kt`: 14 pages as MODELS of what real sites do (the sandbox gets no real site), each with the files a person really wants. Two views: the SHEET's top list (`MediaRank.rank(...).main` that counts: precision = real videos shown / videos shown,
recall = real videos shown / real videos) and the dock BUTTON (gray when the page has nothing to save, lit when it has: only zero / not zero is visible, the number is only in the button's spoken description). The test FAILS when any page loses recall, when the sheet's precision drops below
