# VPS2: what to do with the NoBull P40 VPS (research and plan, 2026-11-26)
Owner, verbatim: "The vps is nobull p.40. Do in depth research and thinking on how this paid vps can improve the apps in any of my repos, improve speed, reduce claude usage, improve app building, run 24/7 testing to improve apps, or anything else that puts the vps to full use and can help with claude or my repos or apps or speeding up my tablet or linkmeter."
Supersedes research/VPS_IDEAS.md. NOTHING is built on the VPS yet: the owner picks the order (VPS2d). Sources are listed at the end; "unknown" means no page said it.

## 0. The short version
1. The VPS is a fast pair of cores that is always on, not a bigger machine. 2 EPYC vCPUs lose to GitHub's 4-core runners on a full Gradle build, and GitHub's standard runners are FREE and unlimited for public repos, so the VPS should not replace GitHub's builds.
2. Its real value is what GitHub and Claude's cloud containers cannot do: stay on 24/7, keep state (caches, fuzz corpora, logs), watch things while no Claude session exists, and send a push message to the owner.
3. Three problems found while reading cost more than any speed gain and need no VPS (section 3, items A1 to A3): the cloud environment's setup script points at a DISABLED repo so Claude sessions have no Android SDK; every session start loads about 14 000 tokens of boilerplate incl. 132 stale "claimed" lines; and the "minutes are scarce" rule is probably wrong for public repos.
4. Two things in NoBull's terms limit the plan (section 2): proxies / anonymizers are prohibited (so no browsing exit server for the tablet without written OK) and gambling / adult / pirated content is prohibited (so nothing that touches the owner's browsing or betting-related repos runs there).
5. Best first steps, in order: A) fix the environment; B) CI watcher + auto-recorder + push messages + nightly diagnostics digest (saves Claude turns, survives container restarts); C) a 24/7 quality farm (fuzzing, real-site Shields canary, list and engine watchers); D) tablet / LinkMeter items (link-quality probes, remote browser for heavy sites like claude.ai, signed list mirror).

## 1. The machine (facts)
- P40 Performance VPS: 2 vCore AMD EPYC, 8 GB RAM, 100 GB NVMe RAID, 1 Gbps port (not burstable), 16 TB transfer a month ($0.02 per GB over), 1 IPv4, KVM, full root, rescue console, 1 free backup, $32 a month ($345.60 a year), 30-day money-back on new VPS orders. Data center: Lumen Seattle 1 (SEA1). OS choices include Ubuntu 24.04 / 22.04, Debian 12, AlmaLinux / Rocky 9.
- CPU model of the P40 is not named on its page; the Performance line uses AMD EPYC 4565P (named for the P10 / P20 trials). A third-party trial of the P20 (same line) scored Geekbench 6 single-core over 1300, overall B, CPU C, disk A, network D (8.97 of 20) and "meets bandwidth specs". The P40 itself was never benchmarked there: MEASURE FIRST (section 6, step 0).
- Node rule: "no new server lands on a node once its average CPU load reaches 60 %" (a placement rule, not a per-VM limit). SLA 99.9 % network uptime, credits capped at 50 % of the month.
- Unknown (ask or test): nested virtualization / /dev/kvm; IPv6 (the host page says no); DDoS protection (host page says no); built-in firewall (host page says no, so run our own); whether the free backup exists (the plan page says yes, the ToS says NoBull takes no backups of customer data: treat the VPS as disposable, git is the backup).
- Compared with the tablet (4 x Cortex-A53) one EPYC core is several times faster; compared with GitHub's standard runner (4 vCPU for public repos) the VPS has half the cores.

## 2. Terms that limit what may run there (NoBull ToS 09/08/2026 and acceptable-use guide 08/15/2026, read through a helper; confirm with a ticket before relying on them)
- PROHIBITED: "proxy scripts or anonymizers", "open proxies and anonymizers" (a VPN / proxy exit for the tablet's browsing is the obvious case; WireGuard is not named; ask), illegal sites, gambling, pornography, pirated software, IP scanners, brute-force tools, mail bombers, IRC bots; outbound SMTP is filtered by default; spam is zero tolerance ($250 an hour remediation); an abusive source may be isolated "first and contact you second"; no refund after termination for attacks.
- NOT mentioned anywhere: CI / build servers, self-hosted runners, 24/7 CPU jobs, crypto mining, per-VM CPU fair use. Silence is not permission: ask in one ticket.
- WHAT THIS MEANS HERE: (a) nothing that carries the tablet's web browsing may run on it by default (the diagnostics show adult, betting and film sites among the owner's pages); (b) the repos Casino, novig, Mirage, and anything that polls betting odds stay OFF the VPS until the owner says what they are; (c) fuzzing, canary crawls of ordinary sites, builds and notifications are ordinary use.
- Draft ticket (owner sends): "I run personal Android app builds, test suites, fuzzing and a monitoring/notification service on my P40. 1) Is nested virtualization (/dev/kvm) available or can it be enabled? 2) Is sustained 24/7 CPU use by one process at 100 percent of both vCPUs acceptable? 3) Is a private WireGuard tunnel between my own phone, tablet and this server acceptable (no third parties, no open proxy)?"

## 3. Where the cost is today (evidence from this repo and this session)
- A1 THE ENVIRONMENT HAS NO ANDROID SDK. The owner's environment setup script is `curl ... raw.githubusercontent.com/tjshea90/novig/main/tools/setup-android.sh | bash --prewarm`. The novig repo is listed by GitHub as DISABLED and cannot be cloned, so the script fails, and every cloud session starts without /opt/android-sdk: ship.sh's local gates (`:app:testDebugUnitTest`, `:geckoapp:compileDebugKotlin`) cannot run, and Gradle offline fails. FIX (no VPS): point the setup script at a working installer. The Launcher and Portfolio repos both carry `tools/setup-android-sdk.sh` (downloads Google's command-line tools, accepts the SDK licences, installs platforms and build-tools). Needs an environment edit the owner approves.
- A2 PER-SESSION BOILERPLATE. The SessionStart briefing is 29 380 bytes (about 7 300 tokens) and CLAUDE.md is 24 388 bytes (about 6 100 tokens): about 13 400 tokens before any work, every session and after every compaction. 132 lines of the briefing are old "[~] claimed" items of sessions that ended in early November. Claude Code's cost guidance says to keep CLAUDE.md under about 200 lines and move workflow detail into skills that load on demand. TASKS.md is 580 KB (the briefing greps it, which is right). FIX (no VPS): print only claims with a commit under 90 minutes old, cap the briefing at about 5 KB, move the long design decisions out of CLAUDE.md.
- A3 MINUTES. GitHub's docs: standard GitHub-hosted runners are free and unlimited on public repositories; larger runners are billed; private repos draw on a monthly allowance ($12 on Free). Browser, Launcher, Keyboard, LinkMeter, Portfolio, scorebox, Optimizer are public. The rule "minutes are scarce" in CLAUDE.md therefore looks wrong for them (the private repos Kestrel-Private and Mirage are the only ones that would pay). ASK THE OWNER whether a bill or a warning ever appeared; if not, the rule can go, which removes the argument for a self-hosted runner and allows free nightly workflows on GitHub too.
- A4 POLLING AND LOST WATCHERS. Each `list_workflow_jobs` answer is 7 to 10 KB; a release needs 4 to 8 of them. The container restarted once today and killed the background tag watcher (re-made by hand). Release recording (`tools/record-release.sh`) waits for a live Claude turn.
- A5 THE DIGEST IS READ BY CLAUDE. `tools/diag_digest.py` prints about 15 KB; Claude reads it in full each time the owner asks "review the diagnostics".
- A6 SUBAGENT RESEARCH is expensive: this research used three helper agents, about 490 000 tokens in total (the Claude docs reading was 348 000 of it). The results are in this file so no session repeats it.
- A7 THE REAL BOTTLENECKS OF THE TABLET are its four A53 cores and the phone's cellular link (weak 5G UW upload in the day). The VPS cannot change either; it can only remove work from them (section 5).

## 4. What the VPS can do, ranked (value for effort; each says what it saves, what it needs, the risk)
### Tier 1: Claude plumbing (build first; cheap, no Claude needed to run)
B1 CI WATCHER + AUTO-RECORDER + STATUS FILE. A small script polls the GitHub API every 2 minutes (outbound only, no open port): lists the newest run per branch of each repo; when a run is red it saves the failing step's last 60 lines to a status file in the private repo (about 2 KB instead of 8 to 20 KB of JSON and logs); when a run with a release is green and the tag has the APK it runs `tools/record-release.sh` with the note from docs/handoff (same steps a session does by hand) and pushes. Saves: the polling turns, the lost-watcher failure, the "wait for the tag" time; a release gets recorded even if the Claude session died. Needs: a fine-grained token (only the listed repos; contents, actions read). Risk: the recorder writes to BUILDLOG.md; run it as its own user; log every action.
B2 PUSH MESSAGES (ntfy, self-hosted, Apache 2.0). The tablet has no Google services so it has no push; the owner's phone and tablet install the ntfy app (F-Droid or the project's APK) and connect to the VPS. The watchers send: build green / red with the Release link, a new diagnostics upload with the one-line summary, the nightly report, a failed job on the VPS. Saves: the owner asking "is it done?", Claude turns spent answering. Needs: a domain or free subdomain and TLS (Caddy), one open port 443. Risk: small; protect with a token.
B3 NIGHTLY DIAGNOSTICS DIGEST. cron runs tools/diag_digest.py and tools/optimizer_digest.py, writes DIAG_TODAY.md (about 2 KB: the drawing mode, crash counts, slow sites, what changed since yesterday) into the private repo, and sends a push message. Only when something got worse (a failing drawing mode, crashes up, a new slow site) does the VPS wake Claude. THE WAKE: Claude's cloud scheduled tasks ("routines") have an official API trigger (HTTP POST with a bearer token; 100 API fires an hour per account; runs draw the subscription like interactive ones). That is the sanctioned unattended path. Saves: one full read of the digest per review. Needs: the routine and its token (stored on the VPS only).
B4 WARM WORKBENCH. Install JDK 21, the Android SDK, the Gradle caches and the repos once. Claude Code on the VPS in tmux, reached from the Claude app with `claude remote-control` (one interactive login by the owner; the docs say remote control needs a subscription login, not an API key, the VPS must stay on and the process must keep running, and it makes outbound HTTPS only). Saves wall-clock (no SDK install, no 429 from Maven, warm Gradle daemon, background jobs that survive), not usage: the usage is the same account. Needs: the owner's login; SSH keys; firewall. Caveat: a cloud (web) session cannot use a folder on the VPS unless the owner has a Team / Enterprise self-hosted environment (the docs' wording); these would be SEPARATE sessions in the app.
B5 MIRRORS AND BACKUPS. `git clone --mirror` of every repo (12, including the private ones) every night, release APKs of the last few versions, and the signing keystores encrypted with `age` (the Portfolio rules call its keystore irreplaceable; scorebox's source was once lost and rebuilt from an APK). 100 GB is plenty. The VPS is the second copy; a third copy belongs on the owner's own computer or another provider because NoBull's ToS says it takes no backups.
B6 REMOTE GRADLE BUILD CACHE (later, measure first). gradle/build-cache-node on the VPS, read by GitHub runners and Claude sessions, written only by the owner's trusted workflow runs (never from pull requests). Gradle test and compile tasks are cacheable, so a run that changed one module skips the others' tests. The workflow already uses gradle/actions/setup-gradle, which caches too: the gain over that must be measured on test-jvm (about 12 minutes) before building this.

### Tier 2: the 24/7 quality farm (what finds bugs while nobody works)
C1 FUZZING THE PARSERS. Jazzer (JVM fuzzer, open source) on core: the filter-list parser, the binary list reader (it reads files that arrive over the network), the URL / omnibox parser, the HTTPS policy, the session codec, LinkMeter's packet and protocol code (Ip4, FastProto, TunStack: it parses raw network bytes) and Swoop's gesture code. A persistent corpus on the VPS grows for weeks; a crash or hang becomes a minimized reproducer file and a push message. Cost to Claude: zero until a finding exists. 2 vCPUs run one fuzzer at a time at thousands of runs a second for small parsers.
C2 REAL-SITE SHIELDS CANARY. The built-in WebExtension (kestrel-shields) runs in desktop Firefox. Nightly, headless Firefox via Playwright loads about 150 sites (the owner's own list from the diagnostics plus common sites) twice, with and without the extension and the current lists, and compares: blocked requests, console errors, visible text length, element and image counts, a screenshot difference. A new rule that hides content shows as a site whose text or images vanished. Today only local lab pages are tested. Limits: desktop Firefox is not Gecko on the tablet; a data-center address gets bot checks on some sites; run at low priority, one page at a time (about an hour for 150 sites).
C3 WATCHERS AND THE LIST COMPILE (this is the old question O11). Nightly: fetch each licensed filter list, parse, compare counts and size with yesterday, check the licence text; compile the .kfs with the existing Gradle tool; sign it; publish ONE small file; look for a new GeckoView release and run tools/check-gecko-prefs.sh against it (the "gecko-watch"). The app must verify the signature and refuse an unsigned list. Saves the tablet seven fetches and the on-device compile after the daily refresh (CPU on four slow cores).
C4 PERFORMANCE TREND. Nightly micro-benchmarks of the filter matcher and the core code, compared with research/lab-baseline.json; the Auto-tune simulation tests; a weekly mutation-testing run (PIT; LinkMeter already has its own mutation scripts). A regression of more than 15 % becomes a push message.
C5 SECURITY HYGIENE. Weekly secret scan (gitleaks) of all public repos and their history, dependency advisories (osv-scanner on the Gradle lock data), lint with the SDK. Public repos with keystores: Portfolio commits app/sideload.jks with the password in its notes; scorebox has a keystore folder; the Browser release key is the public dev key in signing/dev. Anyone can sign an APK with those keys; they are accepted only if the owner installs them. Optional hardening: a private key in GitHub secrets (the Browser pipeline already supports it).
C6 EMULATOR SOAK, ONLY IF /dev/kvm EXISTS. The one-hour hotspot soak and the lab suites currently use GitHub runners (they have KVM). On the VPS they would free no minutes (public repos are free) and add no GPU truth (no Mali). Low value; skip unless KVM exists and a lab needs more than GitHub's 6-hour job limit.

### Tier 3: the tablet and LinkMeter
D1 LINK-QUALITY PROBE SERVER (low risk, high information). nginx on the VPS serves a 50 MB download, an upload sink and an echo for latency and loss over HTTPS with a token. LinkMeter's SpeedTest (it already measures upload with 2 streams and a 64 KB buffer) points at it, and the phone and tablet each run a tiny probe every 15 to 30 minutes (256 KB) and log: download, upload, latency, jitter, loss, band, time of day. The owner's long-standing problem ("almost 0 upload speed during the day with weak 5G UW") then has a 24/7 record: which hours are bad, whether Fast Wi-Fi helps, whether a large download should wait. Costs the phone a few MB a day. Risk: none for the ToS.
D2 REMOTE BROWSER FOR HEAVY PAGES (experiment). claude.ai takes 27 s to load, first paint 13 s, "too busy to answer for 90 % of the load", typing lags: it is CPU-bound on four A53 cores. A Firefox running on the VPS (EPYC core, several times faster) streamed to a Kestrel tab (neko or KasmVNC, WebRTC / VNC; the tablet only decodes H.264 video, which it has in hardware) would take that CPU work off the tablet for the sites that hurt most. Costs: input delay of one round trip, 2 to 4 Mbit/s of video, the login for those sites lives on the VPS (owner-controlled), one browser fits comfortably in 8 GB. Restrict to claude.ai, github.com and similar work sites (NoBull terms). Decide after a one-hour trial with the tablet on the hotspot, then on Fast Wi-Fi.
D3 SIGNED LIST MIRROR: the delivery half of C3.
D4 TUNNEL A/B (only with NoBull's written OK, SYNTHETIC TRAFFIC ONLY). Today the phone's relay opens each connection to the internet itself. A persistent encrypted tunnel from the phone to the VPS, with the VPS opening the connections, would shorten the internet leg of every handshake (about 2 ms instead of 30 to 80 ms) and let one congestion-controlled flow (BBR) fill the cellular link; the gain is guessed at 20 to 40 % on connection setup and unknown on throughput. It also puts NoBull in the path of the tablet's destination addresses and DNS, which a private browser may not want, and it is the "proxy" the ToS prohibits unless confirmed. Measure with iperf3 and a test page only; do not route real browsing.
D5 LINKMETER REMOTE LINK (later): a rendezvous / WireGuard hub so the tablet can reach the phone away from home. Needs the same written OK and a design (research/REMOTE_LINK.md in the LinkMeter repo covers the Bluetooth route).
D6 SCOREBOX: its design is "no backend". A small ESPN cache on the VPS would shrink the feed over a weak link but adds a service to keep alive; only if the owner asks.

## 5. What does not help (so nobody builds it)
- The cut-off pictures and text: the bug is the tablet's Mali driver; no emulator on any host has it.
- Self-hosted GitHub runner for a public repo: GitHub's own security guide says self-hosted runners should almost never be used for public repositories (anyone can open a pull request; the runner can be persistently compromised) and the minutes are free anyway. Build speed: 2 cores are slower than GitHub's 4.
- A local language model on 2 cores with no GPU: far too slow to be worth a turn; deterministic scripts do the digesting better.
- Routing the tablet's browsing through the VPS by default (ToS and privacy, section 2 and D4).
- Unattended `claude -p` loops under the subscription login: the consumer terms forbid access "through automated or non-human means ... except when you are accessing our Services via an Anthropic API Key", while Claude Code's own docs offer `claude setup-token` for scripts; the two are not reconciled in what the docs say. Use the official routines API trigger (B3) for automation, interactive Claude Code (B4) for work, and ask Anthropic support before any cron-driven `claude -p`.
- Anything needing the tablet's own CPU, the carrier cap or the phone's upload signal.

## 6. Order of work and the first day
Step 0 (30 minutes, owner on SSH; I prepare the script in tools/vps/): new non-root user, SSH keys only, firewall (ufw: SSH only, later 443), fail2ban, unattended security upgrades, swap file, timezone; then the benchmark (yabs.sh style: sysbench CPU, fio disk, iperf3 to two public servers) and `ls /dev/kvm; grep -c -E 'vmx|svm' /proc/cpuinfo`; run the P40 for a week before choosing the yearly plan (30-day money-back on new orders).
Step 1: A1 to A3 (environment, boilerplate, minutes question). No VPS needed.
Step 2: B1 + B2 + B3 (watcher, recorder, ntfy, digest). Day 1 to 2.
Step 3: B4 + B5 (workbench, mirrors). Day 2 to 3.
Step 4: C1, C2, C3 one after the other, each with its own time window so two heavy jobs never overlap (2 cores; systemd slices with CPU and memory limits keep SSH responsive).
Step 5: D1, then D2 trial, D3, D4 only with approval.
Capacity: 8 GB RAM is enough for one heavy job at a time (Gradle with the Kotlin daemon 3 GB, headless Firefox 1.5 GB, fuzzer 0.5 GB, ntfy + watchers + Caddy under 0.3 GB, Claude Code 0.3 GB).

## 7. Security design
- A normal user per job class; the canary browser and the fuzzer run in a container with no tokens and no network except what they need; downloaded lists and pages are untrusted data.
- Tokens: fine-grained GitHub tokens limited to the listed repos (contents, actions read); the routine token; the ntfy token. They live in a root-only file on the VPS, never in chat, never in a repo (INBOX / OUTBOX copy chat text).
- The VPS never holds a release signing key. The Claude login on the VPS is the owner's own; sign out on loss.
- Only ports 22 (keys only) and 443 (ntfy, probe server) open; GitHub is polled outbound.
- The VPS is disposable: everything on it is rebuildable from git and a setup script in tools/vps/.
