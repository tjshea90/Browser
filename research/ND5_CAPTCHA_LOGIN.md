# ND5: "Captcha verification failed" on the owner's hosting provider login (owner screenshot, 2026-11-27 ~22:41Z, no words)

What the owner sent: a screenshot of Kestrel G at `my.nobullnetworks.com/login` (the provider's WHMCS client area, template nexus): a red box "Captcha verification failed. Contact support for more information." above an empty email / password form; the Shields badge says 1. The picture stays out of this public repo (CLAUDE.md rule); this file describes it.

## What was established (read-only: the public login page, its public script, Google's public reCAPTCHA anchor page, the 22:42Z upload) [M]
- The page uses Google reCAPTCHA v2 INVISIBLE (`render=explicit`, `btn-recaptcha-invisible` on the Login button, loader `https://www.google.com/recaptcha/api.js?onload=recaptchaLoadCallback&render=explicit`, injected by WHMCS' own script with `jQuery.getScript`). The widget is bound to the Login button: a tap runs `grecaptcha.execute()`, the token callback submits the form.
- The site key is VALID for this domain: Google's anchor page for key + origin returned a normal widget with a token field and no "invalid domain / key" text. So the provider's client-side configuration is fine; a wrong SECRET key on their server cannot be seen from outside.
- The error text is not in the page's script: the server produced it after the form was posted.
- What Kestrel did on that page (the 22:42Z upload, 3 loads of the login page = the first load and two posts that came back with the error): the page loaded fully (15 to 27 requests, `fr=2` = the invisible widget's two frames were created), the Page report says `10 requests, 1 blocked by Shields, no failed loads, no script errors`, and the ONE blocked request is `script www.googletagmanager.com` (answered with a stand-in). Nothing of reCAPTCHA was blocked: our content scripts exclude `https://www.google.com/recaptcha/*` (all 14 blocks of kestrel-shields/manifest.json), the guard only judges pop-ups and cross-site jumps, the filter lists do not touch reCAPTCHA (DefaultListsRegressionTest).
- The owner typed (28 + 7 keys, normal speed), tapped Login about 12 s after the page finished loading and the page came back with the error 3 s later, twice.
- EVERY one of those loads was in the network mode `fast-wifi-tunnel` (the page timing line says `net=fast-wifi-tunnel`; the engine profile is `http3=false noIPv6=true`): the tablet's traffic leaves through LinkMeter's Fast Wi-Fi tunnel, so the provider and Google see a TUNNEL (datacenter) address, not the carrier's.

## What this does NOT say
Whether the same login works in another browser or without the tunnel is not known. The three suspects, in the order they can be told apart by the owner in a minute each:
1. The tunnel's address: reCAPTCHA invisible demands an image challenge for datacenter / VPN addresses (or WHMCS refuses them); a challenge that is not answered gives no token, and the form goes back with exactly this kind of error. TEST: Fast Wi-Fi OFF (the hotspot's own address), reload, log in.
2. Kestrel's Shields on this site: Firefox's strict tracking protection (cookies of Google's frame isolated per site), fingerprinting protection on in normal tabs (`setFingerprintingProtection(true)`, GeckoEngine.kt), our blocker and guard. TEST: the shield badge > Shields off for this site (this turns Firefox's own protection off for the site too), reload, log in. If only this works, switch the single protections to find which.
3. The provider's own configuration (a secret key that does not match): would fail in every browser.

## Next instrument if the tests do not settle it (ND5b, NOT built)
A form-submit probe in `content.js` (top frame only): on `submit`, if the form has a captcha response field (`g-recaptcha-response`, `h-captcha-response`, `cf-turnstile-response`) report the provider and whether the value is empty or its LENGTH CLASS (never the token), via a `cap` message that the background adds to the Page report (`failed` lines), so the next upload says "submitted with an EMPTY token" (the challenge never finished) or "submitted with a token of N characters" (the server refused a real token). Lengths only, no field values, nothing for a private tab.

## 2026-11-27 later: the owner's two tests: "Shields off fixed it" (ND5c)
Result (verbatim): "Shields off fixed it". So it is Kestrel's Shields, not the tunnel and not the provider. What "Shields off for this site" changes in Kestrel G (read in code, not run):
- OURS: the network blocker returns "allow" for the page (`decide`, mode off), cosmetic element hiding is not injected, scriptlets and stand-ins (the Google Tag Manager stand-in) are not applied, the pop-up / jump guard is off (`guard-main.js` `on=false`), the embeds hold is off, the HTTPS policy is off.
- FIREFOX'S: `GeckoSessionSettings.useTrackingProtection` is switched OFF for the tab (`syncEngineProtection`): the strict tracking-protection classification (Disconnect lists: ads, analytics, social, fingerprinters, email trackers) stops for that page. NOT changed by Shields off: cookie isolation (`ACCEPT_FIRST_PARTY_AND_ISOLATE_OTHERS`), fingerprinting protection (`setFingerprintingProtection(true)`, on in normal tabs), query stripping, GPC. The panel's "Block cross-site cookies" and "Block fingerprinting" rows are not used by the Gecko build.
- What was NOT blocked on that page: the Page report names one block (`script www.googletagmanager.com`, answered with a stand-in) and nothing of reCAPTCHA; our content scripts and page-world scripts are excluded from `https://www.google.com/recaptcha/*` (the widget's own frames), the guard's form hook calls the real `submit` once.
- The login script (WHMCS, public): on submit with an empty `getResponse()` it stops the submit and runs `grecaptcha.execute()`; the token callback submits the form again. A submit with an empty token cannot happen through that handler, so the form that came back with the error was posted WITH a token the server refused, or the handler was not bound.
Suspects left, in order: (1) Firefox's strict tracking protection classifying something of the widget (Mozilla's allow-lists are not available in this embedding: GeckoEngine.kt says so for the CONTENT category), (2) the 1,165 generic cosmetic rules hiding part of the widget / its challenge window, (3) the Google Tag Manager stand-in. Told apart by the owner with the Shields panel: keep Shields ON and switch off ONLY "Block ads & trackers" (our blocker AND Firefox's protection), then ONLY "Cosmetic filtering". Also useful: after a failed login, stay on the page and press Send now (the snapshot then names what Firefox's own protection blocked on THAT page: "Firefox's own tracking protection, this page: ...").
