# Video acceleration and smooth video: what other browsers do, what Kestrel G can copy

Research only, 2026-11-16. Nothing was run on the tablet. DOCUMENTED = I read it (source in brackets, no scheme). INFERRED = my reasoning.
Tablet facts: research/TABLET_DIAG_2026-11-16.md and the engine-pref readback pasted in INBOX.md (GeckoView 160: gpu-process on, rdd-process off, android-media-codec on, gfx.webrender.compositor off, video-queue default-size 10).
Gecko pref values below were read on Gecko main (raw.githubusercontent.com/mozilla-firefox/firefox/main/modules/libpref/init/StaticPrefList.yaml), not on 160 itself.

## Summary (10 lines)
1. Chrome puts Android video on its own SurfaceView/SurfaceControl layer that SurfaceFlinger can show as a hardware overlay (no GPU composition of the picture). Gecko on Android has no such path (overlay bugs open since 2019); it draws each frame from a SurfaceTexture, one frame at a time.
2. Chrome decodes into AImageReader buffers; Gecko is migrating (pref gfx.video.aimage-reader-gpu-process-android, GPU-process MediaCodec in 161) but it is unfinished.
3. Rotation: Chrome batches size changes into one update, embeds fullscreen on a black fallback and posts the resize to viz without waiting. Gecko resizes through a synchronous IPC to the compositor, and its Javadoc says surfaceChanged may block. The 0.9-2 s UI stalls are engine-side.
4. Only a Kestrel-owned SurfaceView plus MediaPlayer or Media3 gives the overlay path on this tablet, for sniffed direct URLs (Samsung's popup player works so). No MSE blob streams, no DRM; framework HLS is MPEG-TS only.
5. External players by intent: only MX Player documents a headers extra; VLC and mpv-android document none.
6. Sites do not cap quality to the screen by default (hls.js: capLevelToPlayerSize and capLevelOnFPSDrop false). H.264-only is done; a 60 fps block and a quality cap by extension are the page-level levers. Opera compresses server-side (not possible here).
7. I found no browser that freezes the page behind a fullscreen element.
8. Gecko's ExoPlayer HLS was removed: every HLS page runs hls.js-style script in the one content process.
9. No documented Gecko pref gives overlay or cheaper composition; the prefs below are A/B experiments only.
10. Nothing is measured on the tablet yet; the missing number is dropped frames in full screen.

## 1. Chrome / Chromium on Android
- Decode. DOCUMENTED: MediaCodecVideoDecoder uses asynchronous MediaCodec, prefers hardware decoders, allows 2 pending decodes, and has no low-end branch; its only memory logic reallocates when width grows past 3.9x so MediaCodec's size hints update (chromium.googlesource.com/chromium/src/+/main/media/gpu/android/media_codec_video_decoder.cc). TextureOwner::Create always returns ImageReaderGLOwner (AImageReader), which needs 1 image to mimic SurfaceTexture and 3 with SurfaceControl (gpu/command_buffer/service/texture_owner.cc, image_reader_gl_owner.cc, same host).
- Screen path. DOCUMENTED: the surface chooser defaults to an overlay and falls back to the texture owner when the compositor will not promote, in picture-in-picture, for rotated video, 5 s after an overlay failure, or while a relayout is expected (media/gpu/android/android_video_surface_chooser_impl.cc). Viz comments: "Promoting video to overlay with SurfaceView overlays requires recreation of main SurfaceView and Display"; "we do not have the ability to skip an overlay, since the texture is already in a SurfaceView" (components/viz/service/display/overlay_processor_android.cc, branch lkgr-android-internal). kAndroidSurfaceControl is enabled by default, off when AImageReader is limited to one image (gpu/config/gpu_finch_features.cc); the SurfaceControl processor prefers underlays "because it is more mature on Android" (overlay_processor_surface_control.cc). The overlay was a Dialog holding a SurfaceView made by the GPU process; the older ContentVideoView could not host custom controls and made fullscreen slower (groups.google.com/a/chromium.org/g/media-dev/c/yXFg0DOk67g).
- Android platform. DOCUMENTED: SurfaceFlinger "composes the separate layer as a hardware overlay if supported"; TextureView composites "every visible pixel" twice; protected video must use SurfaceView (source.android.com/docs/core/graphics/arch-tv); "Most GPUs aren't optimized for composition" (source.android.com/docs/core/graphics/implement-hwc).
- Fullscreen entry. DOCUMENTED: Blink locks orientation by the video's aspect (wide = landscape, tall = portrait) when a video goes fullscreen, because users rotated about two thirds of the time (groups.google.com/a/chromium.org/g/blink-dev/c/soUCUMnHcts). Read earlier in this repo: it skips tablets of 600 dp and up; this tablet is 564 dp (research/VIDEO_PLAYER_SOURCES_BROWSERS.md).
- Rotation. DOCUMENTED (chromium.googlesource.com/chromium/src.git/+/HEAD/content/browser/renderer_host/render_widget_host_view_android.cc): during rotation sync is withheld ("Sending each of these separately to the Renderer causes three full re-layouts"), one update is delivered, and rotation ends when the renderer activates a surface at the new size, with a timeout ("on slower devices the timeout may fire before the final signals arrive"). In fullscreen it syncs at once because "the new size is embedded on a black fallback"; fullscreen transitions are throttled 200 ms. WebLayer: "The default resize timeout on Android is 1s", rotation only (chromium.googlesource.com/chromium/src.git/+/refs/tags/106.0.5211.1/weblayer/browser/content_view_render_view.cc). CompositorImpl::SetWindowBounds calls Resize on a mojo remote with no wait; the only sync-IPC comments are in teardown (content/browser/renderer_host/compositor_impl_android.cc). INFERRED: Chrome's UI thread does not wait for viz on a resize.

## 2. Firefox for Android / GeckoView
- Decode. DOCUMENTED: AndroidDecoderModule is gated by media.android-media-codec.enabled; VP8/VP9 use MediaCodec only with hardware support, H.264/HEVC try hardware then software, audio uses ffvpx except AAC (raw.githubusercontent.com/mozilla-firefox/firefox/main/dom/media/platforms/android/AndroidDecoderModule.cpp). NDK AMediaCodec decoding landed in 143 (bugzilla.mozilla.org/show_bug.cgi?id=1934009); GPU-process decoding with RDD as fallback landed in 161 (bug 2080180). On main, media.rdd-process.enabled and media.gpu-process-decoder are Nightly-only on Android. INFERRED: release 160 does not decode in the GPU process.
- Screen path. DOCUMENTED: frames reach WebRender as SurfaceTexture images. media.video-queue.send-to-compositor-size is 1 on Android ("throttled on Android because of SurfaceTexture"), hw-accel-size 3, default-size 10. Bug 1299068: a SurfaceTexture shows only the newest frame, so a buffer is released to the surface only when handed to the compositor. A SurfaceTexture has one consumer and one front buffer (bug 1562818).
- No overlay. DOCUMENTED: bug 1529629 "Use overlay composition for fullscreen video on Android" (reporter: Chrome does it) is still NEW; a SurfaceView overlay needs an extra EGL copy, ASurfaceTransaction (Android 10) could avoid it. Meta 1811424 and bug 1673842 are open; with ASurfaceControl on every tile, commit to callback took 20-40 ms versus about 10 ms for WebGL only. gfx.webrender.compositor is false on Android; the video overlay prefs (gfx.webrender.dcomp-video-hw-overlay-win) are Windows-only. The video-performance meta bug 1889230 lists "extra copies of video frames" and missing compositor fast paths; its Android item 1731414 (Adreno 300 stutter) has no analysis.
- AImageReader roadmap. DOCUMENTED: bug 1649110 (open) wants per-frame AHardwareBuffer access ("video frames were dropped at WebRenderImageHost"); an earlier prototype hit "out of descriptor" crashes. Pref gfx.video.aimage-reader-gpu-process-android exists since 154, behind a pref, default not stated (bug 2048838); bug 2066002 (enable AImageReader with native MediaCodec) is WIP with failing tests.
- Surface and resize. DOCUMENTED: GeckoView defaults to SurfaceView; BACKEND_TEXTURE_VIEW "offers worse performance" (GeckoView.java in the same repo); the architecture doc says TextureView is triple-buffered and needs more memory (mobile/android/docs/geckoview/contributor/geckoview-architecture.md). GeckoDisplay.surfaceChanged: "GeckoSession may block this call to ensure the Surface is valid while resuming drawing". GeckoSession.onSurfaceChanged calls syncResumeResizeCompositor (its Java comment says it "does not block UI thread"), yet PUiCompositorController.ipdl declares sync Pause, sync Resume and sync ResumeAndResize "in lockstep with the application" (gfx/layers/ipc, same repo); GPU-process IPC reply timeout is 10 000 ms. A GeckoView resize also sends new dimensions to the page: "extra restyles, reflows and paints" (bug 1613488). Mozilla called SurfaceView resizing "not synchronized with the rest of the UI" (bug 1594860, WONTFIX). INFERRED: the tablet's 0.9-2 s `ui slow` after a size change is this synchronous wait plus EGL surface work; the Health line "gecko size ... the engine's part took N ms" will show it.
- Other known problems. DOCUMENTED: Oculus Go 1080p60 freeze was CPU starvation, not surfaces (bug 1463904); Moto G5 60 fps skips came from a negative AAudio latency breaking the audio clock (bug 1897302). ExoPlayer HLS was removed and sites fall back to hls.js (bug 1896931).
- Prefs. DOCUMENTED (main): media.decoder.skip_when_video_too_slow_ms 2500, skip-to-next-key-frame true, media.ffvpx-hw.enabled Nightly-only on Android, media.mediasource.vp9.enabled false on mobile, layers.gpu-process.enabled true on Android.

## 3. Samsung Internet, Opera, Brave, Vivaldi, Edge, DuckDuckGo, Focus
- Samsung. DOCUMENTED (search excerpt of a Samsung forum answer; the page itself did not load): Video Assistant's popup player is "an android UI-based video player using Android Media Framework"; it needs the video URL, so MSE sites (videojs, YouTube) cannot use it (forum.developer.samsung.com/t/how-to-support-popup-video-on-samsung-internet/19030).
- Opera. DOCUMENTED: "Rocket Optimizer" shrinks video to the available bandwidth, about 60 percent savings, under Data savings (blogs.opera.com/news/2015/11/how-operas-video-compression-technology-works/). Where it runs is not stated; INFERRED: a server, so unusable here.
- Brave, Vivaldi, Edge, Kiwi: Chromium engines. DOCUMENTED (search excerpts): only background-audio options (Vivaldi 5.7, androidauthority.com/vivaldi-browser-android-3287804/), Brave Playlist on iOS and desktop Nightly (support.brave.app/hc/en-us/articles/360060768611), and since January 2026 YouTube blocks background play in third-party browsers (9to5google.com/2026/02/02/youtube-background-playback-workarounds-not-working-third-party-browsers/). No special decode path found.
- DuckDuckGo. DOCUMENTED: Duck Player is a takeover page "enforcing YouTube's strictest privacy settings for embedded video" (duckduckgo.com/duckduckgo-help-pages/duck-player); not an acceleration.
- Firefox Focus and Fenix: the same GeckoView video path; Fenix sets orientation from media-session metadata (research/VIDEO_PLAYER_SOURCES_BROWSERS.md). Nothing Focus-specific found.

## 4. Sniff the address and hand off
- DOCUMENTED: Firefox add-ons "Stream to Android Player" (detects m3u8, mp4, mpd; Web Share to VLC or MX) and "External Video Player" (addons.mozilla.org/firefox/addon/stream-to-android-player/, addons.mozilla.org/en-US/android/addon/external-video-player). Via, X Browser, Alook, UC, Mixerbox: store pages only; no primary source on their hand-off (viayoo.com/en/ does not mention sniffing).
- Intents. DOCUMENTED: MX Player takes a String[] "headers" extra and a decode_mode byte (sites.google.com/site/mxvpen/api); VLC documents title, position, from_start, subtitles_location, extra_duration (wiki.videolan.org/Android_Player_Intents/); mpv-android documents subs, position, title, decode_mode, no headers (raw.githubusercontent.com/mpv-android/mpv-android/master/docs/intent.html).
- Own player. DOCUMENTED: the framework plays HLS as MPEG-2 TS only, no DASH (developer.android.com/media/platform/supported-formats); MediaPlayer has setDataSource(Context, Uri, headers, cookies) (developer.android.com/reference/android/media/MediaPlayer). Media3 merges headers by priority; browser cookies are not shared, so a Cookie header must be set; per-item headers are not first class (developer.android.com/reference/androidx/media3/datasource/DefaultHttpDataSource, github.com/google/ExoPlayer/issues/6166). `:app` allows no Media3 dependency (CLAUDE.md).
- What breaks. INFERRED from Samsung's statement and research/VIDEO_SOURCES.md section 4: MSE blob streams, DRM, one-time signed links, cookie or IP bound CDNs. Kestrel already replays Referer and Origin sets for downloads (MediaHeaders.sets).

## 5. Other techniques for a weak GPU/CPU
- Codec choice. DOCUMENTED: Enhanced h264ify blocks VP8/VP9/AV1 and optionally 60 fps on YouTube because many devices decode H.264 in hardware only (github.com/alextrv/enhanced-h264ify). Kestrel's VideoPolicy already does the codec part.
- Quality caps. DOCUMENTED: hls.js defaults: capLevelToPlayerSize false, capLevelOnFPSDrop false (threshold 0.2 over 5000 ms), maxBufferSize 60 MB (raw.githubusercontent.com/video-dev/hls.js/master/docs/API.md). INFERRED: the 1920x1080 pick in a 600x947 view (diag) is the site's default; an extension could hide high AVC levels from isTypeSupported or MediaCapabilities (untested, may break players).
- Background tabs: Kestrel already calls setActive(false) (research/VIDEO_SMOOTHNESS.md). Page behind a fullscreen element, timer throttling, memory pressure: no browser documentation found.

## Table: technique, who, can Kestrel use it, expected effect on this tablet
| technique | who does it | can Kestrel use it | expected effect |
| :- | :- | :- | :- |
| Video on its own SurfaceView layer shown by the hardware composer | Chrome (default), player apps, Samsung popup | Own Android view (SurfaceView plus MediaPlayer or Media3), sniffed direct URLs only; no Gecko pref | INFERRED: largest gain (no GPU composition, no page script in the video path); not MSE or DRM; unproven here |
| AImageReader frames, MediaCodec in GPU process | Chrome; Gecko WIP | Gecko pref gfx.video.aimage-reader-gpu-process-android (check the name with tools/check-gecko-prefs.sh), or GeckoView 161+ | Unknown; fewer drops possible; crash risk (open bugs) |
| One frame to the compositor at a time | Gecko Android | Gecko pref media.video-queue.send-to-compositor-size; read first | Raising it is undocumented |
| One batched resize, black fallback, wait for first frame at new size, 1 s cap | Chrome | Own view: keep the cover, lift it on an engine compositor signal (onFirstComposite, unverified), avoid extra resizes (bars, toolbar, keyboard) during the turn | May shorten the 3.1 s cover; engine stall stays |
| Async resize | Chrome | No (sync IPC inside Gecko) | None; only measure |
| Orientation lock at fullscreen entry | Chrome phones, Fenix | GeckoView OrientationDelegate: done | One turn instead of a manual one |
| SurfaceView, not TextureView | Gecko, Chrome | GeckoView setViewBackend: keep default | TextureView composes each pixel twice: worse |
| H.264 only | h264ify family | Gecko pref: done | Hardware decode: done |
| Block 60 fps | Enhanced h264ify (YouTube) | Extension | INFERRED: halves load on 60 fps sources |
| Cap quality to the screen | Players (off by default); Opera server-side | Extension (untested) | INFERRED: 1080p to 480-720p: less decode, memory, bandwidth |
| External player by intent | Firefox add-ons | Own intent; headers only for MX Player | Direct URLs only; extra app |
| Server-side compression | Opera | No | None |

## What I could not verify
- Whether GeckoView 160 has the pref gfx.video.aimage-reader-gpu-process-android, or what its default is (only a bug title).
- Which process drives MediaCodec on 160 (content, RDD, GPU, Java service); main prefs may differ from 160.
- Whether `ContentDelegate.onFirstComposite` ("first content composite after either a start or a restart of the compositor", mozilla.github.io/geckoview/javadoc/mozilla-central/org/mozilla/geckoview/GeckoSession.ContentDelegate.html) fires after a plain resize; whether GeckoView.coverUntilFirstPaint re-arms on resize.
- Whether the sync IPC, not EGL surface work or page reflow, is the main part of the 0.9-2 s stall.
- Chrome's actual rotation timeout (declaration not visible) and its Android Go video adaptations (found none beyond the decoder having no low-end branch).
- Via, X Browser, Alook, UC, Mixerbox internals; Samsung, Opera and Brave current behaviour (search excerpts, 2015-2026 sources).
- Whether media.hls.enabled=true on the tablet is harmful now that the ExoPlayer code was removed (an IronFox issue reports a crash when the class is missing: gitlab.com/ironfox-oss/IronFox/-/issues/226).
- Whether overlay or native player really removes the lag: lab clips decoded with 0 of 150 frames dropped (research/VIDEO_SMOOTHNESS.md), so page script stalls may dominate.
