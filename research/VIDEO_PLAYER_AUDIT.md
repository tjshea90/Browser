## 2. Research: what the proven touch players do (VP1a, report R2 = research/VIDEO_PLAYER_SOURCES_PLAYERS.md; R1 on the browsers' own controls follows)
Read from source and official docs (Media3 PlayerView / PlayerControlView / DefaultTimeBar, Shaka UI, video.js, Plyr, NewPipe, VLC, MX; Android 10 `ViewConfiguration`, `AccessibilityManager`). The behaviours they share, and what Kestrel does:

| Behaviour | The players | Kestrel (core/player/PlayerRules) |
| :- | :- | :- |
| a tap on the picture | toggles the controls (shows if hidden, hides if shown); never play / pause on touch (Plyr only reveals) | `ControlsMachine.tap` |
| single-tap latency | when double-tap is on, the single tap waits the double-tap window: 300 ms (Chromium, Android's own timeout), 500 ms (Shaka), 550 ms (NewPipe) | 300 ms (`DOUBLE_TAP_MS`) |
| auto-hide while playing | 2.0-5.0 s: Chromium 2.5, video.js 2, Shaka 3, VLC 4, ExoPlayer 5, Firefox touch 5 | 3.5 s (`HIDE_AFTER_MS`), longer when Android's accessibility "time to take action" asks (`AccessibilityManager.getRecommendedTimeoutMillis`, API 29) |
| paused / ended / failed | the controls stay until the person acts (all but Firefox) | stay; come back when the film pauses or ends (edge-triggered, so a repeated "paused" report cannot bring them back after a tap hid them) |
| any touch, scrubbing | restarts the timer; scrubbing suspends it | `interacted()`, `pin()` |
| buffering | a spinner; the controls' state does not change | ring over the picture; the clock waits |
| double tap seek | +/-10 s, repeated taps within 0.5 s accumulate (Shaka, NewPipe, YouTube) | left / right third, 10 s, `BURST_MS` 500 ms, flash "+20 s" |
| double tap middle | play / pause (VLC, NewPipe, MX) | play / pause |
| scrub target | a strip 40-48 dp tall around a 2-5 dp bar, a 10-14 dp thumb | 48 dp strip, 3.4 dp bar (5 dragging), 6.5 dp thumb (10 dragging) |
| scrub semantics | Media3: seek on release, never pauses; the others pause while dragging | seek on release (no rebuffer for every move on a 5 Mbit/s link), no pause |
| duration display | only when finite, > 0 and < 2^32; NaN / 0 = unknown; Infinity or 2^32 = live (no end time, no track); re-read on every `durationchange`; a Media Source stream's length is spec-legal short and growing (rises as segments append, shrinks at `endOfStream`) | `DurationView`: KNOWN only when it is not smaller than what is played or buffered AND (for a `blob:` stream) it has stayed the same for 2 s; LIVE for Infinity or 2^32; otherwise only the position |
| ads in the same element | the time bar and seeking are hidden during an ad (Shaka, Media3) | not detected (no page-agnostic rule): an ad's own length shows once it has been stable |
| rotation | keep playing, resume at the same position, handle the change in place (no recreation); no documented "pause while resizing" | Kestrel's own pause + cover until the page has the new size (ROT1/ROT2), controls hidden under the cover and shown for a moment after |
| system bars | hidden bars come back over the content without moving it (Media3 has no inset code) | the controls move up by a pulled-up navigation bar's height (VP3) |

## 3. Research: the browsers' own controls (VP1a, report R1 = research/VIDEO_PLAYER_SOURCES_BROWSERS.md)
Firefox (`videocontrols.js`, `TouchUtils`), Chromium (Blink media controls), Fenix (`MediaSessionFullscreenFeature`). What matters for Kestrel:
* Tap: Firefox toggles on EVERY tap on the empty picture layer (also while paused; hide timer 5 s, fade 200 ms); Chromium toggles after the 300 ms double-tap wait (hide 2.5 s) and never auto-hides while paused, ended, seeking or a menu is open. In both a tap on the bar itself never toggles. Same as Kestrel's design.
* Double tap: Chromium only (a second tap within 300 ms seeks 10 s, left half back, right half forward, clamped to [0, duration], no chaining); Firefox has none. Kestrel: thirds, chaining like Shaka / YouTube.
* Duration: both print `video.duration` as the element reports it and filter nothing (Firefox blanks Infinity); the MSE spec makes NaN, then Infinity, then a short appended-data length a legal sequence. So the "0:04 for a film of a minute" guard has to be Kestrel's own (`DurationView`).
* Orientation: neither pauses on rotation. Fenix locks by the video's shape (portrait video -> portrait, else sensor-landscape, unknown -> user, exit -> user); Chromium locks by `videoWidth` vs `videoHeight` and relaxes 500 ms after the device physically matches. Kestrel's FullscreenTurn already starts a wide film sideways and follows the tablet afterwards (and ROT3 now waits 650 ms of the tablet staying in its position before handing back, the same idea as Chromium's 500 ms).
* Fit: both use `object-fit: contain` in a 100 % x 100 % box over black, deliberately NOT `!important` so page CSS wins. Kestrel's guard forces `contain` only on a full-screen film whose box has another shape than its picture and whose page said `fill` or `cover` (the owner's stretched picture).
* Safe areas: Chromium pads its controls with `env(safe-area-inset-*)`, Firefox does not; Kestrel's controls live in an Android view inside the page area, between the bars.
* Caution: GeckoView's `MediaSession.onFullscreen` can be skipped, so Kestrel detects full screen itself and reads `videoWidth` / `videoHeight` from the page (it does: `player.js`).

## 4. What the emulator lab found about the new controls (suite kp, real Firefox engine on an Android 10 emulator)

* Run 43774881988: the controls draw in portrait and landscape, show at full screen start, hide by themselves, a tap on the picture brings them back and the page never sees that tap.
* Run 43775890786: no result about the controls: that boot of the emulator gave the app a 16 MB java heap (OutOfMemoryError crash loop). The lab now throws such a boot away (it reads the app's `start heap` Health line and starts the emulator again).
* Run 43776782679 (18 of 21 checks green): double tap right / left / middle, mute, exit, the page's own chrome put away and given back, Hide mode start all work. Three findings: (1) a second press on the big button asked "pause" again. Cause: `background.js` wrote the page address into `p` over the film's own `p` (paused), so the app never saw a film as paused; fixed by naming the flag `pa`, and the model now numbers its commands and the page echoes the last carried-out one (`ak`), so a stale report cannot undo a press; (2) the lab tapped beside the 10 s button (its test, not the app); (3) Android 10 sends an app NO event when a sticky-immersive navigation bar is pulled up over the film (picture kp-11 shows the bar over the picture, no visibility callback, no inset change), so in Hide mode the controls' bottom row always keeps the bar's height free.
* Still not measured anywhere: speed on the tablet (the emulator draws with software GL and has an x86 JIT), the real navigation bar of the tablet, the owner's hotspot. The Diagnostics lines "Full-screen video controls", "Turning under a video", "Full-screen page size" and "CPU by process" will say.
