# HW_SPEED - what the MT8168B / 2 GB / hotspot tablet allows, and what is worth tuning (R7)

Written 2026-11-11 by a research agent for TASKS P1 ("as lightweight and fast as possible, snappy ... use the ram and cpu and GPU"). No code, pref or build file was changed; NOTHING here ran on the tablet or an emulator.
Tags: **[V]** read in a primary source (URL given) or in a local GeckoView 160 / repo artifact; **[S]** secondary site or search snippet only (page not opened or not primary); **[U]** my inference. "Main" = Firefox main-branch source (a value may differ from the 160 tag); "160" = read from the real GeckoView 160 `omni.ja` / bytecode / `libxul.so` strings.
Builds on GECKO_SPEED.md, FREEZE.md, ADBLOCK_ENGINE.md, UI_BENCHMARK.md: nothing decided there is repeated (section b lists it by reference). Source line numbers below drift (the code is being edited), so symbols are named. Unverified items are collected at the end.

## Headline (10 lines)
1. **The GPU is not a PowerVR GE8320.** The tablet's own dump says "Mali-G52 MC2" (docs/hardware/hardware_.txt); spec sites list MT8168 with Mali-G52 MP1 @ 800 MHz and put the GE8320 on MT8768 / Helio P22. TASKS P1 and the brief carry the wrong name. Measure `GL_RENDERER` first. Gecko's blocklist disables WebRender for neither GPU. [V dump + GfxInfo.cpp, S web]
2. **Nothing needs "switching on" in the engine**: hardware WebRender, GPU process, MediaCodec decode, JIT, threaded style/raster are already default. Gecko sizes every pool to the 4 cores (Stylo 3, JS helpers 4, WebRender 4+4, TaskController 4) and sets no thread priorities in the pools read: the headroom is contention, memory policy and not wasting the hotspot. [V]
3. **New finding in our code (H1/H2):** `kestrel-shield` (Java priority 4 = nice 10) and `kestrel-io` (priority 3 = nice 13) are moved into Android's BACKGROUND scheduler group by ART/libutils, although Gecko holds every sub-resource request until the shield worker answers and the IO thread also serves URL-bar suggestions. Two-line fix plus an A/B: best expected win per effort. [V mechanism, U magnitude]
4. **CPU:** in-order dual-issue Cortex-A53 (no register renaming, no BTB, 128-bit NEON cannot dual-issue, FP latency 4, DRAM latency >129 ns on a sibling SoC). Expect JS several times slower than a phone-class core [U]; work NOT done (blocked requests, fewer scripts) beats any pref. No evidence for touching JIT thresholds without numbers. [V chipsandcheese]
5. **GPU:** fill rate is not the limit (0.58 MP panel = 35 MP/s per full-screen layer at 60 fps, about 1-2% of peak) [U calc]; the risk is Mali driver bugs (five Mozilla precedents on other Mali parts, none found for G52). Keep the graphics safe mode in reserve. [S]
6. **RAM:** the 128 MB Java heap class does not bound Gecko (native memory). "Using the RAM fully" means keeping private memory LOW so libxul's 118 MB of code and the HTTP cache stay in the kernel page cache: lmkd measures refaults, thrash = jank. GeckoView reacts only at trim levels 15 / 40 / 60 / 80, never 5 / 10 / 20: the app must act earlier. [V 160 bytecode, lmkd doc]
7. **Memory plan (H6/H7):** headroom = `availMem - threshold` from `ActivityManager.getMemoryInfo()`, three profiles (Lean / Balanced / Roomy), a hidden-for-120-s shrink timer, per-process PSS in Diagnostics. All thresholds are starting values [U] until the first tablet report.
8. **Startup:** libxul is 118,043,120 bytes and GeckoView 160 ships no baseline profile. Our own profile helps only our Java side and, for a sideloaded APK, only after the idle+charging dexopt ("likely overnight"). Cheap wins are already in (engine after first frame, `warmUp()`). [V]
9. **Network:** prior advice stands; the biggest page-load lever is still blocking (-78% requests, median load 14 s -> 2 s on a fast link, ADBLOCK_ENGINE). New: metered-aware live prefs, DoH and HTTP/3 as A/B, nothing else. Also drop post-load thumbnails (H3).
10. **Everything is unmeasured on the tablet.** Section (e) is the measure-first checklist, (f) ten Diagnostics A/B switches; the first owner report decides every P2 item.

### What an in-order A53 quad with 2 GB means for a browser
- **JIT tiers:** blinterp (10 runs) -> Baseline (100) -> Ion (1500) [V main]; Ion compiles off-thread on up to 4 helpers that share 4 in-order cores with the main thread, Stylo, WebRender and the TaskController pool. Interpreter and baseline code (dependent loads, no BTB) suffer most on an in-order core; Ion pays only for hot loops. No evidence that moving the thresholds helps [U].
- **WebAssembly on arm32:** explicit bounds checks (huge-memory guard pages are a 64-bit design) plus lazy tiering: expect slower wasm than on phones [S] https://searchfox.org/mozilla-central/source/js/src/wasm/WasmMemory.cpp (mixed-revision comments).
- **GC / parsing:** incremental 5 ms slices, compacting, generational, nursery up to 64 MB, parallel marking off [V 160]; parallel parse and delazify on up to 4 helpers; the bytecode cache (applied, strategy 1) removes repeat compiles.
- **Oversubscription:** about 20 runnable Gecko threads on 4 cores, none prioritised by the pools read; Android's scheduler groups are the only lever and they hit OUR Java threads first (H1, H2).
- **Memory latency:** 130 ns DRAM and a small shared L2 make pointer-chasing DOM/JS slow: smaller working sets and less page work win more than clock speed.
- **2 GB:** the 32-bit address space (3-4 GB per process) is not the limit, physical RAM and lmkd are; the 128 MB class bounds only our Java side.

## (b) Already applied in this repo (by reference, not repeated)
- `geckoapp/src/main/assets/gecko-prefs.txt` v1 (16 prefs) via YAML `configFilePath`, canary read-back in Diagnostics, CI name check `tools/check-gecko-prefs.sh`.

- Packaging: R8 + shrinkResources, arm32 only, no AppCompat. Diagnostics: Health watchdog, FrameMetrics, `MemoryInfo`, low-RAM flag.
- Decided in sibling reports but NOT in code yet (grep, 2026-11-11): `GeckoWebExecutor.speculativeConnect`, `setPriorityHint(HIGH)`, `setParallelMarkingEnabled`, metered-aware media prefs (only the download manager reads `isActiveNetworkMetered`), graphics safe mode.

### Storage and network (Q4)
- eMMC versus hotspot: a cache hit costs milliseconds, a network round trip 100+ ms, so the fixed 512 MB disk cache is a speed feature; eMMC random-read latency is the unknown (H14).
- Session state: GV hands it to the app at most every 10 s (`browser.sessionstore.interval` [V 160]); our save is debounced 600 ms plus `onPause` on the IO thread: fine. Skipping the write when the text is unchanged saves eMMC writes [U].
- Connections: 128 total, 6 per server, pacing on (burst 10, 80 Hz) in this Android build [V 160]: leave; more parallelism hurts a carrier-NAT hotspot [U].
- DNS: cache 3200 entries, TTL 60 s + 600 s grace, TRR timeout 1500 ms per lookup [V main]; DoH needs its own TLS connection first (extra round trips on the first lookups) [U]: A/B in (f).
- HTTP/3 is on with a 100 ms TCP backup timer [V main]: UDP filtering costs at most 100 ms per new origin; read `nextHopProtocol` before changing. Brotli + zstd are advertised on HTTPS [V 160]. `network.prefetch-next=false` stays.
- GeckoView cannot see Android's metered flag; apply the "cellular" media prefs live from an app-side `NetworkCallback` (GECKO_SPEED 3.7, not yet in code).

## (d) Traps: sounds good, wrong on this hardware
| Idea | Why it is a trap here | Evidence |
|---|---|---|
| `largeHeap`, bigger Java heap, "memory boosters", `System.gc()` | Gecko memory is native; the 128 MB class bounds only our Java side; CLAUDE.md bans `largeHeap` | [V] memory-overview, repo rules |
| Raising Gecko thread priority, `sched_setaffinity`, busy loops or wake locks to hold CPU clocks | no API for other processes' threads on API 29; heat; Android Go guidance: avoid wake locks, minimise background activity; `Process.getExclusiveCores()` (API 24) is usually empty | [V] https://developer.android.com/guide/topics/androidgo/best-practices ; Process doc |
| A permanent foreground service to bias lmkd | a notification and wakeups for a benefit only while it runs; today the service exists only during downloads | [V] Go best practices |
| Software WebRender, `layers.acceleration.disabled`, or killing the GPU process "to save RAM" | loses the GPU and the crash isolation; slower on 4 A53 | [U] |
| `fission.autostart` true, higher `dom.ipc.processCount`, `isolatedProcessEnabled` | +RAM per process; isolated processes lose Java video decoders (GECKO_SPEED) | [V] |
| Lowering JIT thresholds, maxing helper threads | more compile CPU on cores the main thread needs; no evidence | [U] |
| More connections: `max-connections` up, pacing off, `speculative-parallel-limit` up | flaky carrier hotspot and 4 cores; this build is already capped at 128 | [V 160] |
| Pre-reading libxul into the page cache at start | competes with start-up I/O on eMMC and evicts other cache on 2 GB; the kernel reads ahead on demand | [U] |
| Hibernating on trim 5/10 or killing the content process on every app switch | every restore re-downloads over the hotspot; use the timer (H6) | [U] |
| `LAYER_TYPE_HARDWARE` on static chrome, shadows, translucent panels | extra GPU memory and overdraw with no animation to pay for it | [V] UI_BENCHMARK 7 |
| Raising refresh rate / frame-rate hints | the panel's modes are unknown, probably 60 Hz only; `Surface.setFrameRate` is API 30 | [U] |
| Disk cache > 512 MB or on removable storage | eMMC wear and space; repeat hits beyond a few hundred MB are rare | [U] |
| Uncompressed libs (`extractNativeLibs=false`) to speed install | +65 MB per update over the hotspot; the project chose the 92 MB APK on purpose | [V] build file |
| Copying "speed" about:config lists | 16 popular names do not exist in 160 and most are desktop-era; `check-gecko-prefs.sh` catches dead names, not useless ones | [V] GECKO_SPEED 2.D |
| Trusting emulator speed numbers | x86 + SwiftShader, relative A/B only | [V] GECKO_SPEED 4 |

In-app Diagnostics additions (on top of GECKO_SPEED 4): GL strings (H4); `Display.getSupportedModes()`; thermal status; `Process.getExclusiveCores()`; nice value and cgroup of each `kestrel-*` thread; shield handler p50/p95 and requests per second; captures per page; `isLowRamDevice`, `getMemoryClass`, `MemoryInfo` headroom; storage test (H14); `/proc/pressure/memory` and `/proc/vmstat` deltas (SELinux may deny apps [U]).
**What the numbers decide**
- Background cpuset is one core, or `cpu.shares` is tiny: H1 and H2 are P0 and A1 may be the biggest single win. Both groups equal to foreground: H1 matters less; look at the Gecko pools instead.
- Governor pinned low or max frequency below 2.0 GHz: nothing to do in the app; reset expectations.
- `GL_RENDERER` is not Mali-G52 (for example PowerVR GE8320): the Gecko GPU rule row still allows WebRender; only GL swizzle is off; no other change.
- `/proc/pressure/memory` absent: legacy minfree mode, `MemoryInfo.threshold` is the kill line, budget = `availMem - threshold`. Present and `some avg10` above 10% in normal use: make Lean the default profile.
- zram in `/proc/swaps`: effective RAM is larger but each swapped page costs CPU; Roomy is less risky.
- Sequential write < 20 MB/s or random 4 KB read > 1 ms [U thresholds]: shrink thumbnail / session writes, keep the cache.
- Shield p95 > 2 ms after H1: escalate the in-extension engine (ADBLOCK_ENGINE R5).
