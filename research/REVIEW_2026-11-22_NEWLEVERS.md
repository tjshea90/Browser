## NL1 (compat, HIGH): Kestrel G does not carry Mozilla's site fixes
[aar] GeckoView 160's omni.ja holds no `webcompat` extension (only FingerprintingWebCompatService.sys.mjs). Stock Firefox for Android gets the built-in "Web Compatibility Interventions" extension (webcompat@mozilla.org) from Mozilla's `feature-webcompat` library, not from the engine. [read] nothing in this repo mentions it (grep webcompat: 0 hits), so Kestrel G is LESS compatible than stock Firefox on every site Mozilla has a fix for.
[aar] `org.mozilla.components:feature-webcompat:160.0.1` (357 KB, MPL-2.0) carries extension 160.4.0: 406 intervention groups, 321 applicable to Android (194 User-Agent header overrides, 129 content-script injections: unsupported-browser banners, desktop layout on phones, FastClick breakage, Office 365 / Outlook, TikTok comments, YouTube back/forward, Nintendo, LinkedIn, CNN, banks), 398 match patterns, 76 tracker shims. All data is baked into run.js at build time (no network needed).
Cost / risk: runs in the engine's parent process (extensionsProcessEnabled is false here), about 340 KB of JS in 13 background scripts, host-filtered webRequest listeners. Its Remote Settings listener would add a new background collection sync: stubbed out (no new background traffic, owner rule); updates then arrive with the monthly engine bump.
Plan (TASKS RVW4-NL1): fetch the AAR at build time from Mozilla's Maven (no third-party code committed), unpack assets/webcompat into the APK, stub the Remote Settings listener, install it with ensureBuiltIn 12 s after the first page (never on the cold-start path), Settings > Site fixes switch (default ON), Diagnostics line.
Not provable here: that every experiment API starts under extensionsProcessEnabled(false) on a real device; the first emulator start must show the extension active.

## NL2 (video finding): the finder can be measured on REAL pages from this sandbox (earlier notes said it could not)
[read] RVW1c / REVIEW_2026-11-20 say "a real-site run is not possible from the sandbox". It is: headless Chromium reaches Vimeo, Streamable, MDN, archive.org, Wikimedia, JW Player, video.js, hls.js (the agent proxy only refuses hosts that have no public DNS). New tool `tools/sitelab/realfinder.js` (not part of npm test: it needs the internet) replays every request / response of a real page into the REAL background.js (fake browser, the web-tests harness idea) and runs the real vfind.js + content.js in every frame, then prints what the finder would tell the app.
First results (2026-11-20, network half + markup half):
- FOUND correctly: Streamable (mp4 + length), hls.js demo (master + both rung playlists), video.js (mux masters), MDN (webm + two archive.org mp4), JW Player (mpd + two webm), Vimeo player (dash master), archive.org (mp4 with length), Wikimedia Commons (transcoded mpd + chunks).
- NL2a (FIXED, core HttpSemantics.probeTotal + test): Wikimedia Commons "File:x.webm" is an HTML page whose address ENDS like a video; content.js reported ~20 page links of that shape (login, history, #sections) as markup addresses and the one-byte verification probe took the PAGE's Content-Length as "the file's size" (any HTML reply of 100 KB or more became a verified video). A text/html or xhtml reply now gives no size, so such a row stays unverified under "Other files".
- Not a defect, checked: `maybe` messages for text/css and images fetched by scripts are the deliberate disguised-playlist probe, budgeted 12 per frame (background.js MAYBE_*).
- Not measurable by this tool: pages that need a login or a consent click (Odysee, PeerTube, Rumble embeds gave no player in headless), DRM, anything that needs a phone UA to serve a different player.
