# SCROLL - stutter, white areas and reloads while scrolling on the MT8168B tablet (R8)

Written 2026-11-11 by a research agent. No code, pref or build file was changed. NOTHING here ran on the tablet or an emulator (no device, no KVM): every statement about speed or frequency on THIS tablet is [U] unless a measurement is named.
Owner complaint: scrolling up and down is slow and stutters; sometimes "it maybe didn't cache properly" and the screen goes white and has to reload; "take full advantage of the hardware, decoding and the GPU".
Tags: **[V160]** read at the Firefox release tag `FIREFOX_160_0_RELEASE` (the tag exists in the mozilla-firefox/firefox mirror, so for the files marked the "main is not 160" doubt of GECKO_SPEED / HW_SPEED is gone); **[Vmain]** read on `main` only; **[Vbin]** read in the local GeckoView 160 AAR (strings = a name exists, omni prefs = a value, bytecode); **[V]** other primary source; **[S]** search snippet; **[U]** inference. Source pages were read through a summarising fetch tool (paraphrase plus quotes of at most 125 characters) and through GitHub code-search fragments (exact lines): behaviour is as those reported, not re-read in full. Builds on GECKO_SPEED.md, HW_SPEED.md, FREEZE.md; their content is not repeated.

## (a) Verdict
1. **Correction (two parts): the decoded-image cache is NOT capped at about 30 MB, and our `max_size_kb` line does nothing.** [V160 prefs] `image.mem.surfacecache.size_factor` = 4 (not 64), `max_size_kb` = 2024*1024, `discard_factor` = 1, `min_expiration_ms` = 60*1000, all `once`. [V160 code] cap = min(physical RAM / size_factor, max_size_kb * 1024), BUT on a 32-bit address space the code first ASSIGNS `surfaceCacheMaxSizeKB = 1024 * 1024;` (exact lines, comment "Limit surface cache to 1 GB if our address space is 32 bit"), overriding the pref. The tablet runs armeabi-v7a, so **our `image.mem.surfacecache.max_size_kb = 98304` is a NO-OP** and the effective cap is min(1.9 GB / 4, 1 GiB) = about 475 MB. The cache is not too small; if anything it is too big for 2 GB, bounded only by the 60-120 s expiry and by pressure flushes. The one lever that works on 32-bit is `size_factor` (`size_factor = 20` gives about 95 MB = what the dead line meant).
2. **Causes ranked by evidence strength** (mechanism evidence first, frequency on this tablet second):
   - (1) **Memory-pressure flushes**: mechanism STRONG [V], frequency UNKNOWN. One `low-memory` drops every unlocked decoded image, empties WebRender's caches ("drastic ... the next frame will have to rebuild all of its resources") and evicts the bfcache; explains "didn't cache properly", white on scroll-BACK and one-frame hitches.
   - (2) **Checkerboarding**: the painted area ahead of the finger is only 1.5x the viewport height on Android (3.5x desktop) [V160], built by a slow content main thread; GeckoView sets `apz.content_response_timeout` to 600 ms [Vbin] (the wait for the page's touch-handler answer; semantics [U]); explains white strips when flinging INTO new content and late scroll starts.
   - (3) **Content process killed** (`onKill`): the literal "white and reloads"; one content process serves all tabs.
   - (4) **Weak CPU / old Mali driver**: Mozilla's own Mali scroll bugs are driver-version and feature dependent (1891831); nothing is known about G52 / MT8168.
   - (5) **Our own overhead**: small each, unmeasured (Q6).
   - (6) **Network blanks** (hotspot + lazy-loaded images + our blocking hook): look like (1)/(2); owner test T1 splits them.
3. **Refuted or weak:** a too-small surface cache; image-decode parallelism (no pref exists; decode runs on the shared TaskController pool [V160]); JS GC on pressure (the pref is OFF on Android [V160]); `onNetworkChanged` reloads (it only retries an error screen, BrowserActivity.kt).
4. **Nothing needs "switching on"**: WebRender, the GPU process, APZ and MediaCodec are the Android defaults [V160]. Real levers: the decoded-image cap (`size_factor`), display-port size, fewer competitors on the UI thread (it feeds Gecko's vsync), and measuring.
5. **Video:** no change needed. MSE VP9 is off on Android (`media.mediasource.vp9.enabled` = `@IS_NOT_MOBILE@` [V160]) so sites get H.264 -> MediaCodec. ffvpx cannot be switched off (no pref in 160) and carries MP3/Opus/Vorbis/FLAC audio. Image decode is CPU only; there is no hardware image decode in Gecko [U].
6. **Next steps in order:** read back the real defaults on the device (A1), add compositor/trim logging and GL strings (A2/A3), run owner tests T1-T4, apply the `size_factor` fix (B0), then A/B the apz display-port rows (B1-B2) and, only if T1 asks for it, `discard_factor` (B3). Do NOT tune blind.

## Evidence by question
### Q1 Surface (decoded image) cache
- **Size:** see verdict 1. `PR_GetPhysicalMemorySize()` = 0 falls back to 256 MB; the code comment says "(size of main memory) / (surface cache size factor) KB" while the arithmetic is in bytes [V160 code]. On this 32-bit build `max_size_kb` is overwritten with 1 GiB before the `min()` [V160 summary; exact lines in the main code search], so RAM / size_factor (about 475 MB) is the binding limit, not our 96 MB.
- **What fills it:** one decoded surface per image at the size it is drawn (downscale-during-decode, JPEG DCT scaling from 2.5x, scaled WebP decode are on [Vmain]); about 4 bytes/pixel, so a 600x400 image = 0.96 MB and 96 MB holds roughly 100 of them. `Insert` fails (and counts `mOverflowCount`) only when one surface does not fit beside the locked ones (cost > max - locked); otherwise it evicts the largest unlocked entries to make room [Vmain]. With a 475 MB cap this practically never happens; with a 95 MB cap still rarely on a 600x973 screen [U].
- **Locked / unlocked** [Vmain]: the cache has no scroll logic; layout calls `LockImage` / `UnlockImage` / `UnlockEntries` as images enter or leave the "visible" range. Unlocked surfaces sit in an `ExpirationTracker` (2 generations, period = `min_expiration_ms`): removed after roughly 60-120 s without a lookup [window U]; a lookup that marks them used renews them.
- **Discard:** `discardable = (max - available) - locked`; freed = `discardable / discard_factor`, largest surfaces first; factor 1 = all unlocked surfaces [V160 code]. The observer reacts to the topic `memory-pressure` whatever the data string (no "ongoing" special case) [Vmain].
- **Scrolling back after a discard or expiry:** the lookup finds nothing -> a new async decode (tasks go to `TaskController` at RenderBlocking priority; DecodePool has no thread count and `image.multithreaded_decoding.limit` is gone [V160]); a PENDING placeholder exists meanwhile [Vmain]. That frame is painted without the image, the page background (usually white) shows, a repaint follows [U for the visual]. Cost on 4xA53: NEON libjpeg-turbo at DCT-scaled size, tens of ms per typical image, 100+ ms for a 2-3 MP photo [U], plus the WebRender re-upload. `imgLoader` also runs `MinimizeCache()` on pressure (unused entries; body not read) [Vmain]; `image.cache.size` = 20 MB bounds that queue [V160].
- **Prefs:** delete the dead `max_size_kb` line and set `size_factor` = 20 (about 95 MB; `once`, YAML only): the decoded-image cache can no longer grow to 475 MB inside a content process on a 2 GB device (less RSS = fewer pressure events and kills) and the visible (locked) set always fits; A/B `size_factor` 12 (about 158 MB) if T1 shows white on the way up without any trim. Optional after that: `discard_factor` = 2 (a pressure event frees half the unlocked images instead of all: fewer blank re-decodes, less relief); leave `min_expiration_ms`. A BIGGER cap cannot help: the cap is not what drops images (expiry and pressure are).

### Q4 APZ / WebRender on Mali-G52 + A53
- **Display port** [V160]: `apz.y_skate_size_multiplier` = `apz.y_stationary_size_multiplier` = 1.5 on Android (3.5 desktop), x 1.25 / 1.5; `apz.prefer_jank_minimal_displayports` true (meaning not verified); `apz.displayport_expiry_ms` 15000; `apz.enlarge_displayport_when_clipped` true on Android; `apz.paint_skipping.enabled` true. At 973 px height 1.5x leaves about 240 px each side (more ahead while moving [U]); a fling of about 3 screens/s outruns that in 100-200 ms, so the content thread must paint within that: on a loaded A53 it often cannot -> checkerboard [U]. GeckoView's file sets `apz.content_response_timeout` 600 (StaticPrefList 400), friction 0.004, max velocity 0.07 in/ms, `touch_start_tolerance` 0.06 [Vbin]; bug 2043753 (Firefox 153 Nightly: stutter when the finger re-touches a fling; regressor "wait for a content response on the first touch-move", backed out) shows that waits on the content thread are felt [V].
- **WebRender defaults on Android** [V160]: `gfx.webrender.batched-upload-threshold` 262144 (65536 elsewhere), `enable-low-priority-pool` false, `program-binary-disk` true [Vmain], `precache-shaders` false, `picture-tile-width/height` 1024x512, `layout.display-list.retain` true, `layout.frame_rate` -1 (vsync), `layers.gpu-process.enabled` true, `layout.lower_priority_refresh_driver_during_load` true. Android is already tuned; no evidence for touching tile sizes or thread counts.
- **Mozilla bugs** [V unless marked]: 1658205 Mali-G71 fling jank during image fade-ins, cause = an APZ sample after scene build using `TimeStamp::Now()`, fixed Firefox 88 (`max-partial-present-rects=0` did not help); 1891831 Mali-G78/G710/A54: about 100 ms scroll latency, 120-150 draw calls, near 100% GPU, whole-page picture-cache invalidation by `backdrop-filter`, drivers <= r38p1 bad and r43/r44 (Android 14) "much better", status NEW; 1732817 apple.com `backdrop-filter` (3 GB phone) [S]; 1697663 Mali-T830, 1711685 Mali-400 software WR [S]; 1694471 time in `eglSwapBuffers`; 1825395 low/mid-end jank [S]. **None names Mali-G52, MT8168 or Android Go** [S, search only]. The tablet's BSP is from 2021, so its Mali driver is probably old and cannot be updated [U]: pages with blur / backdrop-filter headers may be slow regardless of prefs.
- **Fenix on low-end:** nothing scroll-specific found (HW_SPEED lists `fetchPriorityEnabled`, parallel marking by flag, `trimMemoryAutomatically = false`) [U].

### Q5 Video and image decode
- **Order for a video in the content process on Android** [Vmain PDMFactory + AndroidDecoderModule; prefs V160]: the Java MediaCodec module (`media.android-media-codec.enabled` true) is inserted at the FRONT because `media.android-media-codec.preferred` = true; behind it come the remote Utility PDM (`media.utility-process.enabled` true; its own Android MediaCodec is off, `media.utility-android-media-codec.enabled` false), FFVPX and Agnostic. `media.rdd-process.enabled`, `media.gpu-process-decoder`, `media.ffvpx-hw.enabled` are false on Android in 160.
- **Per codec:** H.264 / HEVC (`media.hevc.enabled` true) -> MediaCodec, hardware if the codec list says so (else its software MediaCodec); VP8 / VP9 -> MediaCodec ONLY with hardware, otherwise the module returns null and ffvpx / libvpx software decodes ("software VPX MediaCodecs are not used"); AV1 -> needs `media.av1.enabled` AND hardware in the Java module, software dav1d otherwise (our `media.av1.enabled = false` removes both); MP3 / Opus / Vorbis / FLAC / Wave are always refused by the Android module ("Gecko's own ffvpx decoder is preferred"); AAC takes the general MediaCodec path.
- **Your question:** do not disable software VP9. There is no `media.ffvpx.enabled` or `media.ffmpeg.enabled` in 160 [Vbin], and ffvpx is also the audio decoder. MSE VP9 is already off (`media.mediasource.vp9.enabled` `@IS_NOT_MOBILE@`); `MediaSource.cpp` only offers it when the pref is on or `IsVP9Forced()` (body not read; per bug 1614958 = MP4/H.264 unsupported or hardware decoding unavailable [S]). So YouTube-class sites get H.264 if MediaCodec supports it. Progressive `.webm` VP9 files still decode in software: acceptable.
- **Master switches** [V160]: `media.hardware-video-decoding.enabled` true (`once`), `.force-enabled` false; `media.decoder.recycle.enabled` true on Android; `media.suspend-background-video.enabled` true. `media.video-queue.send-to-compositor-size` = 1 on Android [Vmain]. Surface vs ByteBuffer output is decided in `RemoteDataDecoder` (not read) [U].
- **Image decode** is CPU only (libjpeg-turbo NEON, libpng, libwebp, dav1d for AVIF, JXL); WebRender uploads the result as textures. Prefs that cut cost are already on [Vmain]: `image.downscale-during-decode.enabled`, `image.jpeg.dct-scaling.enabled`, `image.webp.scaled-decoding.enabled`. `image.mem.decode_bytes_at_a_time` 16384 (`once`): leave. `image.decode-immediately.enabled` stays false (true = synchronous decode). Absent in 160: `image.multithreaded_decoding.limit`, `image.decode.defer_if_not_visible` (main only).

### Q7 Chrome-class scrolling vs Gecko
Chrome: the compositor thread "processes input events, performs scrolling and animations" while the main thread works; raster runs as GPU tiles in the GPU process; decode on helper threads; it shows previously rendered content while new content is produced [V RenderingNG]. Tile prioritisation and checkerboard policy are not on that page [U]. Gecko equivalents, all already on [V160]: APZ (compositor-thread scrolling), WebRender (GPU raster of display lists), GPU process, retained display lists, decode on a priority pool. The two knobs that decide whether white appears are Gecko's display-port multipliers (the "tile margin" of Chrome) and the content thread's speed. Chrome's low-end mode keys off <= 1 GB RAM / `isLowRamDevice` (ENGINES.md), so this tablet probably runs it in normal mode [U]. No Chrome-only trick is available to switch on.

## (c) What to measure (adb-free first)
**Owner tests** (same pages each time, 10 minutes): **T1** long image-heavy article, wait until loading stops (60 s), 5 flings to the bottom, wait 10 s, 5 flings back up. White on the way DOWN = checkerboard / lazy-load / network (causes 2, 6); white on the way UP = discarded or expired images / pressure flush (cause 1). ## (d) Traps on this hardware
| Idea | Why not |
|---|---|
| Bigger surface cache (`size_factor` 1-2) | the limit is not what drops images; more RSS = more lmkd kills and pressure flushes; `max_size_kb` is ignored on 32-bit anyway |
| `javascript.options.gc_on_memory_pressure` = true | adds GC / CC at the worst moment; Mozilla keeps it off on Android |
| `gfx.webrender.software`, `layers.acceleration.disabled`, GPU process off | slower on 4xA53 and loses crash isolation; after > 6 crashes Gecko does this itself |
| `image.decode-immediately.enabled` = true | synchronous decode on the paint path |
| Lower `apz.*` multipliers to save RAM | more checkerboarding; the RAM saved is a few MB |
| `dom.ipc.processCount` > 1 / Fission | +RAM per process, more pressure events |
| `lowMemoryDetection(false)` or unregistering GV's controller as a "fix" | Android kills the process instead of Gecko trimming; the runtime still registers its own controller |
| Tile-size / thread-count tweaks (`picture-tile-*`, `render-backend-thread-count`, `stylo-threads`) | no evidence; Android defaults already differ from desktop; four cores are shared |
| `general.smoothScroll`, `toolkit.scrollbox.*` | affect wheel / keyboard, not touch flings |
| Raising `apz.fling_friction` / disabling overscroll | cosmetic; does not change what is painted |
| Disabling ffvpx / forcing hardware-only video | no pref in 160; audio depends on ffvpx; MSE VP9 is already off |
| TextureView backend | composited twice (FREEZE.md) |
| Trusting FrameMetrics jank for page scrolling | it sees only the app window |
| Copying "speed" about:config lists | dead names (GECKO_SPEED 2.D); `check-gecko-prefs.sh` finds missing names, not useless ones |

## R2 update (2026-11-11, alpha7): the display-port multipliers are scaled down by screen size - Firefox's 1.5 is only +16 % here
Owner, request 6: "still stuttering and laggy", "sometimes the scrolling is unresponsive for a split second", "when I scroll down then back up there is just white space for a second".
Read by a research agent in the `main` branch of the mozilla-firefox/firefox mirror (NOT the 160 tag; the pref defaults agree with the 160 read-back on the emulator, the function bodies are unverified for 160) [Vmain]:
- `apz.{x,y}_{skate,stationary}_size_multiplier` is the TOTAL painted size relative to the viewport (centred), and is first scaled down: `multiplier = (multiplier - 1) / alignment + 1` with `alignment = clamp(viewport device pixels / 250, 1, 8)` per axis (`GetDisplayportAlignmentMultiplier`). On this tablet (about 600 x 740 px) the vertical alignment is about 2.9, so Firefox's Android default 1.5 becomes 1.17 = only about 60 px of extra painted page above and below. Anything that scrolls further than 60 px between two content repaints shows an unpainted strip, and scrolling BACK shows the area that was dropped from the display list: this is the white space and the late scroll start. 4.0 gives 2.0x (+-0.5 screen), 3.0 gives 1.7x, 6.0 gives 2.8x.
- `apz.velocity_bias` (default 0.0): shifts the painted window by `velocity * 50 ms * bias` toward the scroll direction. 1.0 = about 110 px ahead at 3 screens a second.
- `apz.displayport_expiry_ms` (15000): "how long after scrolling stops the displayport is removed" (0 = never). After it the page is back to a minimal viewport-sized displayport, and with `apz.prefer_jank_minimal_displayports` (true; it only makes APZ NOT apply the async scroll offset while the displayport is minimal, it does not touch the multipliers) the first scroll after a pause waits for a round trip to the content thread: the "split second" when you start scrolling again after reading. Not verified: the expiry handler itself.
- `apz.content_response_timeout` (GeckoView sets 600): how long a touch waits for the page's own non-passive touch handlers (ad / analytics scripts register them on the document) before APZ scrolls anyway; a busy content thread on 4 x A53 makes that the visible delay. `dom.event.default_to_passive_touch_listeners` does not exist in 160 (checked in libxul and omni.ja).
**Applied (GeckoEngine.applyScrollFeel, live prefs, Settings > Scroll feel, new DEFAULT = level 1):** 0 Standard = the engine's own (1.5 / 1.5 / bias 0 / wait 600 / expiry 15 s / fling 0.07); **1 Smoother = 4.0 / 3.0 / bias 1.0 / wait 300 / expiry 180 s / fling 0.07**; 2 Smoothest = 6.0 / 4.0 / bias 2.0 / wait 200 / expiry never / fling 0.04. Costs: more display-list and tile work per repaint (fewer repaints, though), a few MB of tile memory, images inside the painted area are decoded earlier.
**Diagnostics > "Compare 3 feels (90 s)"** runs the offline scroll test at the three levels back to back and shows the three result blocks in one dialog (Copy): the owner can send numbers instead of impressions.
Emulator sanity check only (software rendering, 11-14 frames a second, so no statement about the tablet): first frame after a touch, median 208 ms (Standard) -> 115 ms (Smoother) -> 95 ms (Smoothest); worst 535 / 382 / 274 ms; the frame rate did not drop (11 / 13 / 14 a second). Order effect not excluded (Standard ran first).
Not measured and not claimable: anything on the real tablet.
