# The blocked-page icon and the one-hand mini navigation panel (AR1, AR2; owner message 32, 2026-11-13)

> "When Kestrel blocks a pop up, instead of the notification on the bottom, put a very small icon in the bottom middle that is not distracting that symbolizes a page blocked, and have it disappear in one second. If I press the icon before it disappears, it still open the blocked page in a new tab without any further prompts."
> "My tablet screen is big, and I sometimes browse with one hand only at the top of the tablet. Make a small quick menu at the top right corner of the screen that is black ... back button on the left, home button in the middle, a forward button on the right, and a bar underneath which when I press it, it selects everything in the url bar and puts a small floating keyboard (or docked to the top right) ... There should be a small toggle at the top right ... slides down ... slides back up ... a very quick light up neon blue ..."

## AR1 - the blocked-page icon (`ui/BlockedChip.kt`, `ic_page_blocked`)

* Replaces the "Blocked a pop-up (host)  Open  Dismiss" bar (`NoticeBar`, 7 s, deleted) and the "Pop-up blocked" toast of the engine's own pop-up prompt (`TabDelegates.onPopupPrompt`, which now also counts the page like every other blocked pop-up).
* ONE icon (a window with a slash), 28 dp inside a 44 dp touch area, bottom middle of the page area, quiet colours (black 80 % disc, mid-blue hairline, muted icon). Shown by `BrowserActivity.onPopupBlocked`; gone 1000 ms after the LATEST block (a second block inside the second restarts the clock; the newest address is the one a press opens).
* A press opens the blocked address in a NEW tab at once (`newTabInternal` + `show` + `navigate`), no sheet, no question. A forced redirect (the page tried to send THIS tab away) is opened the same way, so the page the owner is on stays where it is (before: the notice's "Open" replaced the page).
* An address that is not http / https (an empty window) still shows the icon, and a press only dismisses it.
* Events for Diagnostics: `guard chip-show <kind> <host>`, `guard chip-open <host>`.
* Tests: `BlockedChipTest` (5): one second, restart on a second block, newest wins, one open per press, unopenable address.

## AR2 - the mini navigation panel (`ui/MiniNav.kt`, core `input/MiniKeyboard.kt`)

What it is: a small tab ("toggle", 44 x 26 dp) at the very top right of the page area, always there unless Settings > Appearance > "Mini navigation tab (top right)" is off. Pressing it slides a black panel (176 dp wide) down from the top: **Back** (left), **Home** (middle), **Forward** (right), each 52 x 42 dp, and under them an address bar. Pressing the bar selects the whole address and opens the app's OWN small keyboard under it (the panel grows to 304 dp, anchored at the top right). The toggle slides the panel back up. Open / closed is remembered (`Prefs.miniNavOpen`).

Decisions and why:
* **The keyboard is drawn by the app.** Android lets only the keyboard's own settings move or shrink it; an app cannot ask for a floating keyboard. So `MiniNav.KeysView` draws 4 rows (letters with `/`, `.`, `.com`, space, Go; a `123` page with the digits and `- _ : ? = & % # @ +`, `~ ! * ' ( ) , ;`; shift; backspace that repeats while held) and `core/input/MiniKeyboardModel` decides what a key does (the first key replaces the selected address, Backspace clears it, Go opens it or searches Google exactly like the normal address bar, because it goes through the same `navigate()`).
* **Own clock, not Android's animators.** The owner runs with animations turned off (the neon glow was changed for the same reason, see `Neon`): a system animator would jump to its end. The slide is stepped by `postOnAnimation` from `SystemClock.uptimeMillis()` (200 ms, decelerate in, accelerate out), the lit state of a pressed control is a 130 ms timer. `MiniNavTest` runs the slide with `ValueAnimator`'s scale set to 0 and steps the clock by hand.
* **Neon feedback.** Back / Home / Forward, the bar, the toggle and every key light up in `Pal.accent` (the app's own neon blue; violet in a private tab) for 130 ms when touched, drawn in `onDraw`, no ripple object.
* **Touches.** MiniNav is not clickable itself: only the toggle, the panel's views and (when open) the keys take touches; everything else in the corner belongs to the page. The panel is hidden in full-screen video and the Back key closes the keyboard first (`handleBack`).
* **Buttons act like the dock's:** Back = `handleBack()` (never sends the app to the background from this panel), Home = Home screen (does nothing when Home is already shown, so it does not raise the phone keyboard), Forward = `goForward`. Back and Forward dim when there is nothing to go to; Home is lit when Home is on screen. The bar shows the page's address (tidied: no scheme, no `www.`, no trailing `/`), empty on Home.
* **Gecko build only** (`Flavor.hasMiniNav`); the WebView build (Kestrel Light) has no panel.

Tests: `MiniKeyboardTest` (core, 9), `MiniNavTest` (Robolectric, 13: slide on its own clock, buttons, flash, dimming, bar selects all, first key replaces, Go, shift and symbols, Back closes the keyboard, hiding closes it, unavailable = gone).

What only the tablet can say: whether 28 x 40 px keys are comfortable for the right thumb (the key size is `KEYS_H_DP` and the panel widths `PANEL_*_DP` at the top of `MiniNav.kt`), whether the toggle in the corner gets in the way of a site's own top-right buttons (then it can be switched off in Settings), whether the slide looks smooth on the real GPU.

## AU3 - the mini keyboard types into the web page's own text field (owner message 35, 2026-11-14)

> "Also, if I already have a text field open on a web site, make the mini keyboard enter text into that field instead of searching Google"

The pasted Diagnostics showed the symptom: the mini keyboard's text always went to the address / Google search, whatever the page had focused.

### How a page field can be reached (GeckoView 160, read from the AAR's classes, not guessed)
* `GeckoSession.TextInputDelegate` has EMPTY default methods; the real work is the library's `SessionTextInput.DefaultDelegate` (it talks to Android's `InputMethodManager`). `session.textInput.delegate` returns that default when none was set, so a wrapper can call it for everything and only hold back what the mini keyboard must stop. Set it in `createSession` (UI thread).
* The page tells the delegate three things: `restartInput(session, reason)` (a field gained or lost focus, or its type changed; reasons FOCUS / BLUR / CONTENT_CHANGE), `showSoftInput` (a field wants a keyboard) and `hideSoftInput`. When the system keyboard is already up and a second field is tapped, only `restartInput` arrives (the keyboard re-binds), so "a field has focus" cannot be read from show / hide alone.
* The truth is the editable's own state: `session.textInput.onCreateInputConnection(EditorInfo())` fills the EditorInfo from the focused field (inputType 0 = no field or `inputmode=none`) and returns the connection (null when no field). The library's `GeckoInputConnection` returns ITSELF every time (one object per view); the call only refreshes the EditorInfo and the last selection. It is the same call Android's keyboard makes.
* `commitText(text, 1)` on that connection is what Gboard does to insert: the text lands at the caret (replacing a selection) and the page sees real `beforeinput` / `input` events. Enter and Delete go through `sendKeyEvent` (down + up): the same key events a hardware keyboard sends, so a search box submits and a selection is deleted. `deleteSurroundingText(n, 0)` is used for removing a whole glided word.
* THREAD: the editable asserts it is used on its "IC thread". `ic.handler` (the no-argument `InputConnection.getHandler()`; for the library's connection it is the UI handler when a hardware keyboard is present, else its own background looper) also TELLS the editable which handler that is. So every operation is `ic.handler.post { ... }`, exactly as the Android framework does for a keyboard; posts to one handler stay in order.
* `EditorInfo.imeOptions & IME_FLAG_NO_PERSONALIZED_LEARNING` is set for a private tab: the keyboard learns nothing there.

### The design
* `PageFieldInput` (geckoapp) wraps the session's TextInputDelegate. While the mini keyboard is up (`held`) it swallows `showSoftInput` and `restartInput` (so the system keyboard never covers the mini one); `hideSoftInput` always goes through. It counts focus changes (`generation`) and tells the activity so the panel can follow a field that appears or goes.
* The panel talks to it only through the small `PageField` interface in `:app` (the WebView build has none: `navPageField()` is null there), so MiniNav stays free of GeckoView types and testable with a fake.
* Opening the keyboard with a page field focused = field mode: the bar starts EMPTY (the address is not selected), says "type into the page" and carries a small "page" tag; keys, glides, candidate swaps and Backspace are applied to the same text model as before and the DIFFERENCE (characters removed from the end, characters added) is sent to the field. A Backspace beyond what was typed here deletes the page field's own text. Go presses Enter in the field (a one-line field also closes the keyboard, a multi-line one stays open). A password field shows dots in the bar and is never learned from. A private tab is never learned from (also in address mode).
* If the field goes away (the page navigated, the field was blurred) the keyboard falls back to the address bar behaviour; if another field is tapped, typing continues there with a fresh text buffer. With no field focused nothing changes: address or Google search as before. To type an address while a field is focused, tap the page outside the field (or use the main address bar).

## AU1 - the invisible long-press corner (owner message 35; `ui/HotCorner.kt`)

> "make the top right slide down box with the navigation panel and keyboard have no visible button at all. Instead, if I long press the top right corner of the browser (make it a decently large target square to long press, but invisible), it slides open the panel and if I long press above the open panel it slides it back closed."

* The small visible tab is gone. The top right square of the page area, 72 dp (about 12 mm) a side, is the long-press target. The panel hangs just BELOW that square, so "above the open panel" and "the corner" are the same place: the same long press opens and closes it (`MiniNav.toggle()`).
* `HotCorner` only WATCHES: `BrowserActivity.dispatchTouchEvent` shows it every event first and the page gets them all (a tap on a link under the corner, a scroll, a pinch work as before). Only a finger that stays down inside the square, within the touch slop, for 380 ms acts: the page is told its touch is over with a synthetic ACTION_CANCEL (the engine's own long press, about 500 ms, never starts: no context menu, no link follow), a short haptic tick, the panel toggles, and the rest of that touch is kept from the page. It is inactive while a video is full screen, over another screen or sheet, and when Settings > "Mini navigation panel (long press the top right corner)" is off.
* The clock is the TOUCH's own as well as a timer. Found on the emulator: when the UI thread is busy (software rendering: seconds per frame) the events reach the app late and all at once; a 800 ms press was taken for a tap and followed the link under the corner. The move or the lift now carry the answer (event time minus down time at least 380 ms: it was a long press). Still possible: a quick tap that lands while the UI thread is blocked for more than 380 ms can be taken for a long press (the panel toggles instead of the tap); on the tablet's normal speed this does not happen.
* Emulator proof (Android 10 x86_64, software rendering, animations off, lab page `tools/sitelab/fieldlab.py` with a link in the corner): an 800 ms stationary press opened the panel, another closed it, neither followed the link under the corner (the lab server log shows no request); a short tap there followed the link (`search q=cornerlink` in the log); a drag that starts in the corner and a drag elsewhere left the panel as it was. Screenshots were looked at, not kept (the repository is public).
* Tests: `HotCornerTest` (13): a still long press fires once and the rest of the touch is kept; a tap, a drag, a second finger and a wobble inside the slop; a long press whose move or lift arrives late fires from the timestamps; a late lift of a short touch is still a tap.

## AV1 - resize by the corners, detach and move (owner message 36, 2026-11-14; `ui/MiniNav.kt` `PanelLayout`)

> "make the mini keyboard resizeable by dragging corners. Make it able to detatch and i can move it around the screen if possible."

* **What the person sees.** A short bar (the GRIP) sits in the middle of the top edge of the panel; four small L marks hug the outside of the panel's corners while the keyboard is open. Drag the grip: the panel leaves the corner and follows the finger (the bar lights up while it is away from the corner). Drag a corner: the keyboard gets wider / taller (left corners keep the right edge, right corners keep the left edge, top corners keep the bottom, bottom corners keep the top); the key labels grow and shrink with the keys. Let go of the grip within 40 dp of the corner, or double tap the grip: the panel docks again (the size is kept). Settings > Appearance > "Reset the mini keyboard's size and position" puts back the corner AND the first size. Everything is saved.
* **Geometry.** `gRight` / `gTop` (the OUTLINE's distance in dp from the right edge and the top of the page area), `gW` (the width while the keyboard is open, first 304 dp) and `gH` (the height of the rows of keys, first 161 dp); stored as four integers in `Prefs.miniGeom` (null = docked at the first size). They are clamped for DISPLAY only (a smaller page area for a moment does not move the panel for good). Limits: width 232 to 620 dp and at most the page width; key rows 100 to 320 dp.
* **The band.** The panel view is 16 dp bigger than its outline on every side (`BAND_DP`, transparent). A touch that goes down in the band belongs to the PAGE (the panel's `dispatchTouchEvent` returns false) except on the grip (56 dp either side of the middle) and, while the keyboard is open, within 26 dp of an outline corner but OUTSIDE the 6 dp frame, so the Go, 123 and Backspace keys at the corners are never taken. `HotCorner.Host.covers()` keeps the long press of the invisible corner from firing on the panel when the panel sits over it.
* **The decoder.** The key boxes come from the same function that draws them, so a new size only needs the decoder told the new key positions: `prepareGlide()` is held back while a corner is being dragged (`resizing`) and runs once at the end.
* **Found on the emulator and fixed.** (1) Setting a background drawable takes the padding from it, so the new transparent inset replaced the frame padding and the bar and keys ran to the outline: the padding is set again after the background. (2) A property initialised after the `init` block overwrote the stored geometry with its defaults: `loadGeometry()` now runs in an `init` placed after the fields. (3) The lift's own position was not applied: events that arrive late (a busy screen) lost the last bit of the drag.
* **Emulator proof** (Android 10 x86_64, software drawing; real touches by `adb input swipe`): the grip drag moved the panel across the page and it stayed there; opening the keyboard there put it at the same right edge and top with the four corner marks; dragging the bottom left corner outward made the keyboard wider and taller with bigger labels; a glide on the resized keyboard typed "hello" with the right guesses (the decoder took the new key positions); dragging the grip back near the corner docked it again at the new size.
* **Tests.** `MiniNavTest` (Robolectric): starts docked where it always was; the grip moves, saves, and the keyboard opens where it was left; cannot be dragged off screen; drop near the corner and double tap dock; a corner drag resizes and the keys still type and glide; right and top corners move the right edge and the top; minimum and maximum sizes; corners only grabbable with the keyboard open and the band is the page's; reset; geometry survives a start. `HotCornerTest`: the corner does not fire over the panel.
* **Not run:** the tablet's real touch feel (the 26 dp corner zones and the 44 dp grip are guesses sized for a thumb), landscape, and one-handed reach with a big keyboard. The 16 dp band is the page's: a link right beside the panel can still be tapped; only the outline, the grip and the open keyboard's four corners take a touch.


## AY2 / AY3 / AY4 - long press on open space, the space key moves the cursor, a panel that floats (owner message 39, 2026-11-14)

> "For the top right corner navigation panel, make it so I can long press anywhere in the browser and it will show up under where I long pressed, but only if I am long pressing an open space. If I'm long pressing a link, give me the options for that link, not the navigation panel. If it doesn't already do so, make the navigation panel keyboard space key able to move the text cursor if I press and hold it then move my finger left or right, just like other keyboard apps do. Make the navigation panel a floating panel which I can move around easily by long pressing it and dragging it around"

### What the engine does with a long press (found on the emulator with `tools/sitelab/presslab.py`, a lab page with every kind of target)
* GeckoView reports a long press to the app (`ContentDelegate.onContextMenu`) only for a link, a picture or a media element. A long press on BLANK space is not reported to Java at all, so the app cannot tell open space from "nothing happened".
* The page DOES see it: every long press arrives as a trusted DOM `contextmenu` event (blank space, text, a button, a field, a link). No `click` follows a long press. On a link or a picture the app opens its own menu and sends the page a touch cancel; on text the engine selects the word under the finger about 250 ms AFTER the `contextmenu` event (the event comes first).
* So the page's own script (the built-in extension's `content.js`) is the one place that can tell what is under the finger, and it tells the app only when the answer is "open space".

### How the app decides (`content.js` -> `background.js` -> `ShieldsBridge` -> `BrowserActivity.onOpenSpace` -> `MiniNav.showAt`)
* `content.js` listens for `contextmenu` (capture phase, trusted events only) and looks at the whole stack of elements under the finger (`elementsFromPoint`, ten deep, so a transparent layer over a link does not hide the link). Not open space: a link with an `href`, a picture, a video, audio, canvas, iframe, form control, button, label, summary, an editable region, a widget `role`, an element with `onclick` or a tab stop, and anything whose computed cursor is `pointer` (the usual sign of a clickable card).
* A press on text is not open space either: the engine selects the word under the finger about 250 ms AFTER the event, so `content.js` looks at the selection 200 ms later: a NEW, non-empty selection means text. Found on the emulator: when a word was selected already and the press is on blank space, the engine CLEARS the old selection (after the event), so "the selection changed" is not the test; the test is "a new selection exists" (a first version used "changed" and the panel did not come in exactly that case). A press on the text that is selected already (nothing would change) is recognised by the position of the selection's rectangles.
* A wrapper that fills the whole screen (95 % wide, 90 % high) does not count through its `onclick` or tab stop (an app root with a tab stop would otherwise make every spot of the page "not open space"); its tag, role and pointer cursor still count.
* What is sent is `{k:'os', p: address}` and nothing else (no coordinates, no page content). `background.js` swaps the address for the top page's (a frame's long press counts for its tab). The app checks the message is about the tab in front, is fresh (the touch is still down, or lifted less than 2 s ago) and did not travel far, cancels the page's touch (nothing is clicked or selected when the finger lifts), gives a haptic tick and puts the panel under the finger.
* **Under the finger** (`MiniNav.showAt`): centred on the finger, the panel's top edge 26 dp below it (`SHOW_BELOW_DP`), kept inside the page area, no slide. When the panel was open somewhere else it moves there; the place is saved like any place the person moved it to. The keyboard, when open, stays open.
* **Where the page cannot answer** the old touch detector (`HotCorner`, 380 ms, still finger) stands in, now over the WHOLE page area: Home, an error screen, a page the extension does not run in (not http/https, a PDF), a tab without a session, and a page that is stuck in a slow script (it cannot answer anything). `Host.covers` keeps the detector away from what has its own long press: the open panel, Home's search box, its Go button and suggestions, the buttons of the error screen.
* **How the panel closes.** The corner long press that used to toggle it is gone. A TAP on the grip (the short bar on the top edge of the panel) closes it, sliding up. A long press on open space while it is open moves it there. Settings > "Mini navigation panel" still switches the whole thing off.
* Tests: `web-tests/openspace.test.js` (12, real headless Chromium with a fake extension API: blank space, every kind of interactive element, widgets by role, a full-screen wrapper, a transparent layer over a link, a link beside blank space, text with the engine's selection simulated, an existing selection that stays, one that the engine clears, a press on selected text, a made-up event, an app that does not answer); `MiniNavTest` (`showAt`).

### AY4 - a floating panel (`MiniNav.PanelLayout`)
* A long press (400 ms, `PICK_MS`) on the panel itself - the buttons, the bar, the frame between them - picks it up: the button or bar under the finger is sent a touch cancel (so it does not act when the finger lifts), a haptic tick is given, the outline lights in the accent colour, and the finger carries the panel anywhere on the page; it stays exactly where it is put (the old "drop near the corner and it snaps back" is gone; "Reset the mini keyboard's size and position" in Settings still brings it back).
* The KEYS are never picked up: they keep their own long press (a held top-row letter types its digit) and the glide. The grip and the corners keep their direct drag (no long press needed).
* A short tap on a button or the bar acts as before. A finger that moves before 400 ms, or a second finger, ends the wait. The event's own clock counts as well as the timer (events that reach a busy UI thread late still pick the panel up), the same way `HotCorner` does it.
* A tap on the grip closes the panel; a drag of the grip moves it.
* Tests: `MiniNavTest` - a long press on the bar and on a button picks up and carries (and the button is not pressed), a short tap still presses, a long press without a move does nothing but light the outline, a quick drag from the bar moves nothing and the timer is taken away, the timer picks up with no later event, the keys keep their long press (the digit), a second finger ends the wait, the keyboard stays open while the panel is carried, a drop near the corner stays where it is, a tap on the grip closes.
* A touch that ends after a long press that showed the panel used to leave the neon glows held still (they are held while a finger is down and released by the touch's end, which the swallowed touch never reached; the same was true of the old corner long press): `BrowserActivity.dispatchTouchEvent` now releases them when a swallowed touch ends.

### AY3 - the space key moves the text cursor
* Press the space key and slide the finger sideways: after 10 dp it is a cursor slide (no space is typed), and every 11 dp moves the cursor one character, with a tick. In the address bar the keyboard's own cursor moves (the bar draws the caret there, scrolling the text around it); in a page's text field the page's own caret moves (the arrow keys are sent, and what was typed so far is handed to the keyboard's memory first). Lifting without sliding types the space as before.
* Core: `MiniKeyboardModel.cursor` / `moveCursor` (typing, Backspace and a glide now work at the cursor; surrogate pairs are never split). Tests: `MiniKeyboardTest` (8) and `MiniNavTest` (space slide: no space typed, steps per distance, a slide in a page field sends the arrow keys).

### What was run on the emulator (Android 10 x86_64, software drawing, real touches written to the input device by `tools/emu/glide_emu.py holddrag|slide`) and what was not
Run: blank space -> the panel moved from the corner to under the finger (bar centred on the finger); a link -> the link menu (Open in new tab / private tab / Copy link address / Share link) and the panel stayed; a linked picture -> the link menu; a plain picture -> the picture menu; text -> the engine selected the word, the panel stayed; a button, a text field and a clickable div -> the panel stayed; Home's open space -> the panel came under the finger, Home's search field -> it did not; a long press on the panel's bar then a drag moved the panel by exactly the finger's distance and it stayed; a tap on the grip closed it; a slide on the space key in a page text field sent three ArrowLeft keys and the next letter landed three characters back (`abcdef` -> `abcxdef`), the same in the address bar (caret drawn after `abc`); a page that runs a script for 50 s: the engine asked after about 30 s, the app logged `slow-script-waited` and showed nothing, the script finished and the page was usable.
Not run: the tablet itself (its touch feel, the real long-press timing of its Android build, a thumb's slop), a PDF, an iframe with a real address (the lab iframe is `srcdoc`, where the extension does not run), landscape.
