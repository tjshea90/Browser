## 2. What was changed (alpha110) and why
### 2.1 Settings opens at once (SET1)
Evidence: `ui STALL 2360ms` at 04:58Z, in `SettingsView.rebuild`: about 130 rows with long explanations, each a row + two TextViews + a Switch, all built and measured on the UI thread of a 4 x Cortex-A53, on every open and on every `rebuild()` after a switch (Neon, phone helper, drawing...).
Change: `SettingsView.section(title) { rows }` builds a section's rows only while the section is open; Settings opens with the headers only (47 views to build and measure in the web build against 265 with everything open; Kestrel G has more rows, so it gains more), a tap on a header opens or closes it, the open sections are remembered until the app is closed and survive `rebuild()`. The "Last successful check" date no longer goes through `DateFormat.getDateTimeInstance()` (830 ms the first time per run: it loads the phone's locale patterns) but through core `LocalStamp.format` (plain arithmetic, JVM-tested against `java.time` on 20,000 random moments and zones). Tests: `SettingsLazyTest` (6, Robolectric), `SettingsPhoneSwitchTest` (2, opens every section first), `LocalStampTest` (3).
NOT run on the tablet: how it feels; the stall should be gone (47 views instead of 265 to build and measure), the first tap on a big section (Network lab, about 25 rows) builds in one go.

### 2.2 A restored preview carried no page (TP1 hole)
Evidence: the 05:17Z Diagnostics said `Tab previews: 2 tabs, 1 with a preview, 1 for the WRONG page (must be 0)`. `BrowserActivity.restore` gave the selected tab its saved preview (`sel.thumb = selThumb`) without `thumbPage`, so the tab counted as wrong, and the next address update (`Tab.url` setter: "thumbPage != page of the new address") threw the picture away. `ThumbStore.load` has already proved the picture was taken for this very page, so the tab now owns it WITH its page (one line).

### 2.3 Keep the page ready while the app is away (KR1)
Evidence (section 1, "Engine kills"): the engine's content process was killed 7 times in 17 hours, always while Kestrel was in the background and only after 15-69 minutes; MemAvailable was 540-980 MB around the kills (Android 10 Go's killer takes CACHED processes first, at free-memory levels near 215-315 MB; a foreground service moves the app up to the "perceptible" class, which dies near 108 MB), and each return then reloaded claude.ai for 25-30 s and lost the page's state (a half-typed message).
Change: Kestrel G starts one quiet foreground service when the app goes to the background and ends it when the app comes back, after the chosen time (Settings > Appearance > "Keep the page ready when I leave": Off / 15 minutes / 1 hour (default) / 3 hours), when the task is swiped away, or by the notification's "Let go" button. Nothing is loaded or sent by it. See `KeepReadyService`, core `KeepReady` (rule + tests), `ProcessLife.keepReady`.
Cost, said plainly: the engine's memory (about 300-600 MB with a heavy page) stays in use while the app is away, so other apps are asked to give way earlier; the notification is silent and has no status-bar icon.
How to check it: the digest's KILLS section (new) separates kills by "app was away" and "keep ready on"; after a day with it on there should be none while the service ran.

### 2.4 The digest and the self-checks
- `tools/diag_digest.py`: SETTINGS TO CHANGE counts only advice from the newest build family (retired rules from alpha94 no longer shout), and prints `SELF-CHECKS`: every snapshot line that says "(must be 0)" with a non-zero number (this would have caught the WRONG preview automatically).
- A KILLS section: content-process kills with whether the app was away and whether keep-ready was on.

## 3. Considered and NOT done (evidence too thin or no safe change)
- claude.ai's first paint: no setting in the Auto-tune catalog moved it (inside the noise on small pages, never measured on the real page). An A/B on the real page and a profile are the next instrument (section 4).
- `Classifier Update` thread at 78-97 % of a core 11-26 s after a cold start in 7 of 80 runs: the owner decided to keep Safe Browsing updates (2026-11-20, "keep the p4 traffic"); not touched.
- NET_PARTIAL_TRANSFER on claude.ai (14 times, 4 in the newest upload): xhr responses cut short; the page works afterwards. The engine does not say why (LinkMeter tunnel, carrier, or the site). No change; the Page report in Diagnostics keeps naming them.
- First start after an install ends within 25 s (alpha107, 108, 109): DG1_FIRST_RUN_AFTER_INSTALL.md; still no cause; still an install-time effect.
- `ui slow` stalls with an idle stack: system pressure.

## 4. The missing instrument (not built here): a real profile of the page
GeckoView 160 and 161 have `ProfilerController.startProfiler(String[] filters, String[] features)` and `stopProfiler(): GeckoResult<byte[]>` (gzip JSON). Nobody has used it (GECKO_TUNING_2.md item 1 said "measure first"). A one-tap "Profile this page" in Diagnostics (start, reload the page, stop when it settled, keep a summary by thread and category plus the heaviest script files by host, upload through the live-diagnostics channel, never in a private tab) would turn "the page is busy" into "X % parsing, Y % garbage collection, Z % layout, script file F". The format of the returned bytes has not been seen here, so the first step is to capture a file and look at it. Open as TASKS ND1d.
