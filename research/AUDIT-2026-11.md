# AUDIT-2026-11 - app and engine audit for the owner's tablet (TASKS X4, X5, X12)

Written 2026-11-12 during alpha15/alpha16. Owner report (message 10): "very slow loading Proton mail and lagged when I was typing ... well coded and extremely efficient and optimized for my hardware. Consider looking at the Firefox engine it is using and modifying it for maximum speed on this hardware."
Evidence tags: **[V]** verified in this session (code read, test run, emulator), **[E]** estimate, **[N]** not verified (needs the real tablet). NOTHING in this file was measured on the MT8168B: the only device available is a software-emulated x86 Android 10 (about 30x slower than the tablet in wall time, useless for absolute numbers). Companion documents: `research/GECKO_TUNING_2.md` (engine research, 190 lines, by a research agent, 440 pref names checked against the bundled 160), `research/ADBLOCK_ENGINE.md` (blocking engine decision), `research/DOWNLOAD_MANAGERS.md` (download research), `research/D1-DESIGN.md`.

## 1. Verdict in plain words
1. **Modifying / recompiling Firefox: no.** GitHub's runner (4 vCPU, 14 GB, 6 h cap) cannot build Gecko, Mozilla's own shipped armv7 build is already profile-guided (a home build without PGO would be SLOWER), and the only no-compile engine change with a measurable effect is trimming `omni.ja` (about 9 MB of the 92 MB APK: update size only, not speed) [V research/GECKO_TUNING_2.md section 1, 4].
2. **The engine configuration is already close to what preferences can give** on 4 x Cortex-A53 / 1.9 GB (one content process, bounded image cache, bytecode cache after 2 loads, no AV1, no push, JitHints and off-thread Baseline are defaults in 160, no socket process on Android, eager parsing is off below 2 GB RAM). One hygiene pref added (`browser.translations.enable=false`, v3 of `gecko-prefs.txt`; the pref name is checked against the bundled engine by `tools/check-gecko-prefs.sh`) [V].
3. **What I cannot know without the tablet is where Proton Mail's time goes.** The honest plan is: measure first (new Diagnostics "Page loads"), give the owner two switches that decide the biggest unknowns of a hotspot connection (DNS over HTTPS, HTTP/3), and change things on numbers, not guesses.
4. **Typing lag in a page has no per-key code of ours in the path** [V: no `TextInputDelegate`, no `onCreateInputConnection` override, no per-key listener in `:geckoapp`/`:app`]: the path is Android IME -> `GeckoEditable` -> Gecko main thread -> the page's JavaScript. Proton Mail's composer is a React app with debounced encryption in workers on a 4-core in-order CPU [E]. The levers that exist: no UI-thread stalls (the watchdog counts them: `ui.late`, `ui.stall` in Diagnostics), no extra work in the page (our content scripts are tiny, capture-phase, idle-scheduled), no resize of the page when only the address bar is typed in (done in alpha3: `adjustNothing` while the address field has focus).

## 2. What was audited and what was found
| Area | Finding | Action | Status |
|---|---|---|---|
| Per-request blocking | Used to cost a native round trip per request (the suspected freeze source). | Decision now made inside the extension (alpha13, D1): JS port of the Kotlin engine over a binary image, 0 mismatches on 156k real requests, counters batched. | shipped [V] |
| Extension content scripts | `content.js` + `guard-main.js` (alpha15) run in every frame at `document_start`: small, capture-phase listeners only; the new page scan (`content.js`) runs at idle, reads at most 300 KB of inline script text, reports at most 40 addresses. | Kept deliberately cheap; Shields off for a site switches the guard off. | shipped [V emulator], cost on the tablet [N] |
| UI refresh path | `applyUi()` runs on every progress step; the new "Save video" chip rebuilt a sorted list and a new drawable on each call. | Early exit when the page saw no media, nothing rebuilt when colours and count are unchanged. | alpha16 [V compile/tests] |
| Neon / animation | Holds still while a page loads or the keyboard is up (`updateNeonBusy`); no other animation exists. | none needed | [V code] |
| Keyboard | The address field switches the window to `adjustNothing` and a 100 ms probe lifts the dock; in a PAGE field the window uses `adjustResize`, so the page resizes ONCE when the keyboard opens (a relayout of a big single-page app). | Candidate: keep the page size and scroll the field into view instead (Chrome's "resizes-visual" behaviour). Needs measurement before touching the typing path. | open [N] |
| Startup | `Application.onCreate` starts the engine (filter image + public-suffix list) on a background thread; the first page competes with it for the 4 cores. | Daily list refresh is delayed 90 s after the app comes to the front (`maybeRefreshLists`), so it never competes with the first page. | alpha16 |
| Network path | DNS over HTTPS first (`network.trr.mode` 2) with a 1.5 s timeout and HTTP/3 are both defaults; on a carrier hotspot either can add a stall per new host [E: research/GECKO_TUNING_2.md 2.3]. | Settings > "Network lab": two live switches (DoH on/off, HTTP/3 on/off), applied without a restart (`GeckoPreferenceController.setGeckoPref`). | alpha16 [V emulator: log `network-lab doh=true http3=true`] |
| Measurement | No per-page timing existed. | Diagnostics > "Page loads": host, time to first paint, time to load finished, requests blocked, visit number (hosts only, private tabs not recorded, last 14, memory only). | alpha16 [V emulator] |
| Memory | One content process, `surfacecache.size_factor` 20, `max_total_viewers` 2 (alpha3). RAM per process is unmeasured. | Diagnostics already lists processes; owner numbers wanted. | open [N] |
| Downloads | The download engine ran with a fixed ramp and could fail a whole download when ONE extra connection was refused, or after 1-3 minutes of a dead hotspot. | See section 4 (X3). | alpha16 [V tests] |

## 3. What I need from the owner (zero code on the owner's side except tapping)
1. **Proton Mail numbers.** Open mail.proton.me, wait until it is usable, open Menu > Diagnostics and copy the "Page loads" lines (or tell me them). Do it twice (the second visit shows what the caches save). Then Settings > Network lab: switch "Encrypted DNS" OFF, restart the browser, repeat. Then the same with "HTTP/3". One change at a time.
2. **Shields off for proton.me** (Shields panel) and load again: it separates the cost of our blocking extension from the engine.
3. **The tablet itself:** which keyboard app (Diagnostics prints it), whether an accessibility service or an autofill service is on (both slow Gecko's typing path), battery saver, free storage (an install and the caches need room), the hotspot band (5 GHz is much better than 2.4) and the phone's signal.
4. If typing still lags on proton.me but not on a plain page (for example this site's Diagnostics page or a simple textarea): say so; the next step is Gecko's own profiler (`ProfilerController` exists in 160) with a typing lab page, which I will add as a Diagnostics button.

## 5. X5 ad and tracker blocking: is it the best available?
**Where Kestrel G stands** (details and measurements: research/ADBLOCK_ENGINE.md): network blocking with EasyList, EasyPrivacy and the uBlock Origin lists in a compact hash-based engine (the same verdicts in Kotlin and in the extension's JS port), cosmetic element hiding, per-site switches, HTTPS upgrade, cookie and fingerprint protection from Firefox's own Enhanced Tracking Protection (strict), plus since alpha15 a pop-up and forced-redirect guard that no list-based blocker has by design (it decides on the real tap, not on a URL).
**What the best blockers have that this does not yet** (research/ADBLOCK_ENGINE.md sections 6-9): scriptlets (uBlock Origin's `+js()` rules, the thing that beats video-site ads and anti-adblock walls), neutered redirect resources, `$removeparam`, procedural cosmetic filters (`:has-text`, `:xpath`), generic cosmetic filtering from the class/id index. Estimated 15 session-days for the lot; the plan and order are in that document (P1).
**Decision:** keep the own engine (uBlock Origin itself cannot be hosted by GeckoView's extension API without a lot of missing browser UI, and Brave's Rust engine has no maintained WebAssembly build). Auto-update: the lists are refreshed EVERY DAY now (conditional requests: an unchanged list costs a few hundred bytes), a failed or suspicious list never replaces the working one (size check and canary URLs), and the daily dialog mentions the refresh.
**Owner decision wanted:** a scheduled GitHub workflow that compiles the lists once a day into one small file would cut the tablet's list traffic from seven requests to one, move the compile off the tablet and let new rules (for example for movie sites) reach the tablet without an app update. Repository rule: no workflow triggers except tags and manual dispatch without the owner's OK. A `schedule:` trigger is a different kind of trigger; I did not add it.

## 6. What changed in alpha15 and alpha16 for speed (summary)
alpha15: pop-up/redirect guard (fewer ad pages and background tabs = less work), page scan with idle scheduling. alpha16: lists refresh outside the first minute of use, cheaper UI refresh, Page loads timing, Network lab switches, translations actor off, download engine changes above. None of them is claimed to make Proton Mail faster: that needs the numbers in section 3.
