## 5. Part V - video

### RX4-V1 - fullscreen video turns the screen sideways (P1, S-M)

**Evidence [R]:** `GA/BrowserActivity.kt` `fullScreenChanged` (about line 2467) only hides the dock and the system bars (`applyImmersive`); a search for `OrientationController`, `OrientationDelegate`, `onOrientationLock`, `requestedOrientation` in `GA`, `APP` and `app/src/main` finds nothing. GeckoView has the callback: `OrientationController.OrientationDelegate#onOrientationLock(int): GeckoResult<AllowOrDeny>` and `onOrientationUnlock()` (set on the runtime's orientation controller; the engine's own tests set the activity's `requestedOrientation` and allow) ([W] Javadoc, bug 1697647). one bug comment says Fenix never implemented it ([W]; treat as unconfirmed, it does not matter for this app). The activity already declares `configChanges="orientation|screenSize|..."` so a rotation does not recreate it. Effect today: on the 600x973 tablet a landscape film in fullscreen is shown 564 dp wide by about 317 dp high; YouTube and most players call `screen.orientation.lock('landscape')` on their fullscreen button, and with no delegate the request can have no effect [N: check on the emulator what a lock request does today, a no-op or a rejected promise; either way the screen does not turn].

**Change:**
1. `GeckoEngine.create` (after the runtime exists): set a delegate on the runtime's orientation controller [N: confirm the accessor name with `javap` on the 160 AAR; the Javadoc lists `OrientationController` in `org.mozilla.geckoview`]. `onOrientationLock(o)`: allow only while a page is in fullscreen (`BrowserActivity.fullscreenOn`), map with a pure `CORE/session/OrientationMap` (Gecko value -> `ActivityInfo.SCREEN_ORIENTATION_*`; unknown -> deny), set `requestedOrientation` on the UI thread, answer allow; `onOrientationUnlock()` -> `SCREEN_ORIENTATION_UNSPECIFIED`. Leaving fullscreen always unlocks.
2. Auto-landscape without a site lock: on `fullScreenChanged(true)`, if the tab's playing video is wider than tall (the app already has `rw` and `rh` from `content.js` `vid` facts in `VideoFlow`, RX3-V1) and no lock was requested within 600 ms, request `SCREEN_ORIENTATION_SENSOR_LANDSCAPE`; on exit restore the previous value. Settings > Video row "Turn the screen sideways for full-screen video" (default ON; off = only what a site asks for).
3. Check the pref the engine uses for this: `dom.screenorientation.allow-lock` was switched on for GeckoView Nightly ([W] bug 1767449); add it to the read-back list in `GeckoEngine.readBackPrefs` and, if the 160 release value is false, add `dom.screenorientation.allow-lock = true` to `geckoapp/src/main/assets/gecko-prefs.txt` (bump `kestrel.config.version`, run `tools/check-gecko-prefs.sh`).
**Proof:** `CORE` mapping test; a Robolectric test that the delegate denies outside fullscreen; a lab page in `tools/sitelab` with a video and a "lock landscape" button; on the emulator `adb shell dumpsys activity activities` shows `requestedOrientation` changing and back (RX4-E1 can run it). Tablet: one tap on a film's fullscreen button.
**Risk:** the mini panel, the neon halo and `HotCorner` run while the layout flips: test rotation with the panel open. **Do not:** lock orientation outside fullscreen; keep the rotation lock the owner set in Android (a lock request on a device with auto-rotate off is still honoured by the app, as in Chrome).

### RX4-V2 - OWNER QUESTION: audio when the app is left (P3, M, do not build before the answer)

## 6. Part X - secure browsing

### RX4-X1 - a fake "Kestrel update" must not install over the app (P1, S-M)

**Evidence [R]:** `signing/dev/kestrel-dev.jks` and its password are public (SEC-1; B1 needs the owner's GitHub secrets, still open). Android treats an APK signed with that key and package `app.kestrel.browser.gecko` as an UPDATE: it keeps cookies, sessions and permissions. A web page can download such a file in the browser (the owner's habitual sites are free-streaming sites: fake "update your player", "install the app" buttons). `BrowserActivity.download()` (about line 2679) asks only the generic text for risky types ("can install software or run code. Only continue if you trust the site"); opening from the Downloads list (about line 2758) the same. Nothing looks inside the APK.
**Change:** a pure rule in `CORE` (`ApkIdentity.verdict(pkg, signerSha256, ownPkg, pinnedSha256, cameFromUpdater)`) and an Android reader `APP/diag` or `GA/net/ApkInspect` using `PackageManager.getPackageArchiveInfo(path, GET_SIGNING_CERTIFICATES)` (API 28+, minSdk is 29) on the IO executor: (1) package equals the app's own id or starts with `app.kestrel.` and the file is NOT the one `UpdateManager` produced (it knows its own file names and sha256) -> refuse to open from the Downloads list, offer only "Delete", text "This file says it is Kestrel but did not come from Kestrel's own update screen. Do not install it."; (2) any other APK -> replace the generic text by facts: app name, package, how many permissions it asks for and the dangerous ones by name (SMS, contacts, accessibility, install packages, overlay), and "the file is signed by a certificate not seen before on this tablet" (compare with `signing/CERT_SHA256` only for rule 1); (3) a file whose extension or type says video/image/pdf but whose first bytes are a ZIP with `AndroidManifest.xml` is treated as an APK (the extension can lie; Android opens by MIME). Run the check when the download FINISHES (so the warning is on the row) and again at open.
**Proof:** `CORE` table test (own package from updater / not from updater / other package / not an APK); a Robolectric test with a tiny fixture APK; emulator: put a debug APK signed with the dev key in Downloads under a video name, open it from the list -> refused. **Risk:** low; the updater's own file must still install (test it). Until B1, this is the only brake on the attack.

## 8. Part N - page loading

### RX4-N1 - the 250 ms wait before a navigation (P2, S; histogram first)

**Evidence [R]** (`EXT/background.js`): `onRequest` for a `main_frame` calls `slBefore(h)` (lines ~541-543). When the host already has an early scriptlet registration (`slReg.get(host)` exists: YouTube and every site with `site##+js()` lines) and the call is for a main frame, `slBefore` returns `Promise.race([slAsk(host), later(SL_WAIT_MS)])` (lines ~403-411, `SL_WAIT_MS = 250`, line ~346), and the request is held until it resolves: a second native message `sc` (the first is `cfg`, sent in the same moment and not awaited, line ~541) to the app's `kestrel-shield` thread, answered after parse and lookup. Comment in the code: the wait exists so a Shields switch change reaches the next load cleanly. Typical cost [E]: tens of ms (UI-thread hop plus the shared `workerHandler` queue with `cfg`, `pend`, `rep`, `cnt`, `st`, `media`); worst case the full 250 ms at the start of every such navigation, exactly when the UI thread is busiest (keyboard closing, panel, glow).
**Change:** (1) M0c histogram first. (2) If p95 > 40 ms: make `cfg`'s answer carry the host's scriptlet fingerprint (the same string `sc` returns, or its hash) so one round trip covers both and `slBefore` for a main frame waits only on the `cfg` promise that is in flight anyway; or keep the old registration without waiting when the Settings and per-site switches are known unchanged (the app can bump a small `epoch` that `cfg` answers carry; a changed epoch means "wait this once"). Keep the late hand-off from `content.js` as the safety net (already there). **Proof:** `WT/background.test.js` cases (no wait with a fresh epoch; one wait after an epoch change; a Shields-off reload still clean); emulator lab (E1) timing of `main_frame` start with and without. **Do not** weaken the "reload after a switch is clean" rule.

### RX4-N2 - revalidations on a 5 Mbit, high-RTT link (P2, S; counters first)

**Idea [E]:** every conditional request (`If-None-Match` / `If-Modified-Since`, answered 304) costs a full round trip (100-300 ms on a hotspot) and a pages carries dozens of them on a revisit when servers send `no-cache`, `max-age=0` or only `Last-Modified` with short heuristics. The extension already sees every request and has a blocking `onHeadersReceived` listener (`rcv`). **Step 1:** M0b numbers. **Step 2 only if the owner's Diagnostics shows >= 8 revalidations per revisited page costing >= 400 ms:** a Network lab switch "Keep static files fresh longer" (default OFF) that rewrites the response `Cache-Control` of `script`, `stylesheet`, `font` and `image` responses that have an `ETag` or `Last-Modified`, no `no-store`, no `private`, no `Set-Cookie`, not `Vary: Cookie`, status 200, same-site or well-known CDN, to `max-age=600` (scripts, styles) / `86400` (fonts, images), never for documents, XHR/fetch, or private tabs; the `Reload without cache` action and a Shields-off site bypass it. Risk: stale scripts breaking a site until the TTL ends: hence conservative TTLs and OFF by default. This is the same mechanism BK5 (no-store -> no-cache) would use: build it once.
